# Extension architectures: how other harnesses let code extend them

Research date: 2026-11-15; provider follow-up and approved direction added 2026-11-16. Source reading of primary docs and code at the snapshots below; no external system was built or run, and no feature is claimed to ship in a release unless stated. Measurements of Bun placement options are a separate study: [`bun-topology.md`](bun-topology.md).

**Status:** the original comparative evidence remains a historical baseline for Track 5 in [`plan.md`](../plan.md). The [provider follow-up](#provider-follow-up-2026-11-16) distinguishes newer source snapshots; [approved direction](#approved-direction-2026-11-16) records decisions, not implemented behavior.

## What axo is measuring against

The 2026-11-15 yardstick, clarified by the approved 2026-11-16 scope:

- **Extend axo without writing Rust.** Within named contributions and in-session operations, extensions reach the same supported capabilities and semantics as the public Rust surface ([Rust extension traits](../../crates/axo/docs/extending.md#3-rust-extension-traits)). This is not parity with every host power: host singleton services, session lifecycle ownership, trust and host UI answers remain host-owned. Agent-layer driver traits are not automatically session-pluggable hooks.
- **TypeScript/JavaScript on Bun** is the chosen authoring environment.
- **User-authorized code may override host defaults.** Installed code can replace built-ins; collisions need provenance and a resolution rule, not an inherent host veto.
- **Shared Rust changes over TS-only restrictions.** If the existing Rust composition cannot express what an extension needs, the shared Rust surface changes.
- **The Rust API already dictates state and lifecycle** (session ownership, journal, branches, child sessions); extension semantics follow it rather than inventing new ones.
- **Host-neutral.** Extension roots and acquisition come from the host like every other configuration input; nothing assumes a GUI or TUI.
- **Now settled:** process-per-extension placement, opt-in user grouping, failure/restart policy and packaging phase boundaries; see [approved direction](#approved-direction-2026-11-16). The original survey did not decide them.

Out of scope: model-written scripts (codemode, Track 1). An embedded engine such as Boa is of interest there, not as a replacement for Bun.

## Five separate decisions

Every system below makes five choices that are easy to conflate. They are independent:

| Choice | Options seen |
|---|---|
| Author language | One host language (OMP, pi, Claude, OpenCode: TS/JS); any language (Octet, Goose MCP); Rust → Wasm (Zed) |
| Package and install | npm/git with a real dependency install (OMP, pi, OpenCode); vendored, no bare npm imports (Claude); author ships the whole runtime closure (Octet); package manager of the server command (Goose MCP); prebuilt Wasm archives (Zed) |
| Runtime placement | In-process callbacks (OMP, pi, OpenCode); Claude documents in-process execution but not its internal thread/isolate topology; subprocess per extension/binding (Octet, Goose stdio MCP); in-process Wasm store per extension (Zed) |
| Transport | Direct function calls (in-process systems); JSON-RPC over stdio (Octet); MCP (Goose); WIT component calls (Zed) |
| API authority | Tool/resource/prompt interoperability (MCP) versus broader harness operations; provider/OAuth, lifecycle, session and UI coverage differs across the full plugin systems below |

Two consequences matter for axo:

- **RPC does not force polyglot authoring.** Octet speaks a language-neutral wire but gives authors one-language helper SDKs; a TS-only SDK over an internal RPC bridge is a coherent design.
- **MCP does not force a subprocess, and a subprocess is not a sandbox.** Goose runs built-in MCP servers in process over in-memory duplex streams. Merely launching a process does not remove the user's OS authority; optional containers or other restrictions must be assessed separately.

## OMP

- **Shape.** An extension is a trusted TS/JS module exporting a factory `(pi: ExtensionAPI) => void | Promise<void>`. The Bun host imports it and calls it in the same process; the API is real callbacks, not a serialized protocol ([guide](https://github.com/can1357/oh-my-pi/blob/7c49c11aa5bbaf3f418406583096168ad5b8c6dc/docs/extensions.md), [loading](https://github.com/can1357/oh-my-pi/blob/7c49c11aa5bbaf3f418406583096168ad5b8c6dc/docs/extension-loading.md)).
- **RPC is a client interface, not the plugin ABI.** OMP's JSON RPC mode lets an external program drive the agent; its SDK embeds the agent in a Bun process. Neither is how extensions are authored or loaded.
- **Breadth.** Tools (with progress, cooperative `AbortSignal`, late registration, activation), `tool_call`/`tool_result` interception (block, rewrite arguments or results, flip the error flag), input, system-prompt and context rewriting, raw provider payload replacement, finalized-message rewriting, stop/continuation control, subagent spawn gating, custom messages and persisted custom entries, settings with source provenance, commands, shortcuts, renderers and TUI components.
- **Providers and OAuth.** `registerProvider` adds or overrides base URL, keys, headers, model catalogs (static or fetched), usage reporting, a custom `streamSimple`, and callback-based OAuth (`login`, `refreshToken`, `getApiKey`, `modifyModels`). Secret prompts are rejected over RPC; the SDK host must honor or reject them.
- **Install.** Drop a file in a project or user extension directory, pass `-e`, or install an npm/git package declaring `omp.extensions`. The installer runs OMP's own binary as Bun (`BUN_BE_BUN=1`), so standalone OMP needs no separate Bun; it runs `bun install`, then validates factories by **executing** them on a throwaway registration surface, rolling back on failure ([installer](https://github.com/can1357/oh-my-pi/blob/7c49c11aa5bbaf3f418406583096168ad5b8c6dc/docs/plugin-manager-installer-plumbing.md)). Validation runs trusted code; it is not a sandbox. Install-state writes have no cross-process lock.
- **Lifetime.** Imports run concurrently; factories run sequentially in path order; dedupe is by absolute path, not realpath. Factories are rebound per child or new session, but **module globals stay shared**. Settings changes suspend and resume already-imported sources without unloading them; newly enabled sources need a restart; same-process reload relies on mtime-tagged import URLs, which Windows Bun ignores ([loader](https://github.com/can1357/oh-my-pi/blob/7c49c11aa5bbaf3f418406583096168ad5b8c6dc/packages/coding-agent/src/extensibility/extensions/loader.ts#L124-L200)).
- **Conflicts.** `registerTool` may shadow a native tool; `ctx.invokeTool` reaches the same-named native built-in. Host-RPC and SDK tools beat extension tools. Registrations carry `sourceInfo`. Collision rules differ per registry (first link scheme wins, last shortcut wins), and some host winners are hardcoded ([wrapper](https://github.com/can1357/oh-my-pi/blob/7c49c11aa5bbaf3f418406583096168ad5b8c6dc/packages/coding-agent/src/extensibility/extensions/wrapper.ts#L65-L149)).
- **Failures.** Most handlers get 30 s; `tool_call` fails closed. A timeout ends the host's wait but **does not stop the JS or undo its effects**. A raw timer throw or unhandled rejection can kill the whole session; managed `ctx.setTimeout` routes errors to the extension channel ([runner](https://github.com/can1357/oh-my-pi/blob/7c49c11aa5bbaf3f418406583096168ad5b8c6dc/packages/coding-agent/src/extensibility/extensions/runner.ts#L140-L210), [background work](https://github.com/can1357/oh-my-pi/blob/7c49c11aa5bbaf3f418406583096168ad5b8c6dc/docs/extensions.md#background-work-ctxsetinterval--ctxsettimeout)). `before_agent_start` may rerun up to three times; only the winning attempt's context publishes, but external effects of losing attempts remain.

## pi

- **Shape.** Same factory model as OMP, loaded with jiti and no build, in the pi process with full user authority ([guide](https://github.com/earendil-works/pi/blob/c3cc91632d0a1950fb122605b190233f2aa0006e/packages/coding-agent/docs/extensions.md#writing-an-extension)). `pi --mode rpc` and the SDK make a host a **client** of pi; a Rust program using RPC does not become a pi extension.
- **Breadth.** A [typed event list](https://github.com/earendil-works/pi/blob/c3cc91632d0a1950fb122605b190233f2aa0006e/packages/coding-agent/src/core/extensions/types.ts#L1638-L1714) covering trust, resources, MCP changes, session start/switch/fork/compact/tree/shutdown, context and full-request rewriting, provider headers/payload/response/stream, agent and turn boundaries, messages, tools, model selection, input and user bash. Plus commands, flags, shortcuts, renderers, providers with custom streaming and OAuth, virtual models, MCP server registration, nested `ctx.executeTool` that goes through validation, hooks and policy.
- **Composition.** Handlers are awaited serially in load order, then registration order, chaining returned values. Some callbacks must return **synchronously** (`prepareArguments`, `reachesTools`, `prepareLoadout`, renderers, OAuth `getApiKey`); an out-of-process API must treat these explicitly rather than serialize event names ([types](https://github.com/earendil-works/pi/blob/c3cc91632d0a1950fb122605b190233f2aa0006e/packages/coding-agent/src/core/extensions/types.ts#L597-L710)).
- **Install.** `pi install npm:…@version | git:…@ref | path`, user or project scope. Managed packages install runtime `dependencies`; host packages are peer dependencies aliased to pi's own copies, so classes and registries are not duplicated. Identity is the npm name, normalized git URL, or absolute path; project entries replace global ones ([packages](https://github.com/earendil-works/pi/blob/c3cc91632d0a1950fb122605b190233f2aa0006e/packages/coding-agent/docs/packages.md#understand-scope-and-identity)). Project extensions load only after project trust and cannot grant it themselves.
- **Lifetime and state.** Replacement (`/new`, `/resume`, `/fork`, `/reload`) shuts down the old instance, invalidates captured contexts, and rebinds a new runtime ([runner](https://github.com/earendil-works/pi/blob/c3cc91632d0a1950fb122605b190233f2aa0006e/packages/coding-agent/src/core/extensions/runner.ts#L727-L742)). Branch-sensitive state is rebuilt from `getBranch()` on `session_start` and `session_tree`, not from all entries ([state](https://github.com/earendil-works/pi/blob/c3cc91632d0a1950fb122605b190233f2aa0006e/packages/coding-agent/docs/extensions.md#state-management)). `turn_end`/`agent_before_settle` handlers propose persisted entries and continuation; the result is validated but **not transactional** ([boundaries](https://github.com/earendil-works/pi/blob/c3cc91632d0a1950fb122605b190233f2aa0006e/packages/coding-agent/docs/extensions.md#turn_start--turn_end)). The factory cache creates fresh instances, but module globals are not session-local.
- **Children.** The shipped subagent **example** launches a separate `pi --mode json` process; parent extension instances are not inherited ([example](https://github.com/earendil-works/pi/blob/c3cc91632d0a1950fb122605b190233f2aa0006e/packages/coding-agent/examples/extensions/subagent/README.md)).
- **Conflicts.** Cross-extension tool names: first wins. Extension tools override built-ins silently. Shortcuts: last wins with a diagnostic. `replaceable: true` built-in extensions (codemode, tool search, MCP) step aside on collision ([runner](https://github.com/earendil-works/pi/blob/c3cc91632d0a1950fb122605b190233f2aa0006e/packages/coding-agent/src/core/extensions/runner.ts#L640-L719)).
- **Failures.** Handler errors are reported and later handlers run, except `tool_call` (blocks) and `user_bash`. No general handler or factory deadline was found in the loader or dispatcher. An extension can block the event loop or crash the process; there is no separately isolated extension process to restart.

## Octet

- **Shape.** Rust owns execution, conversations, persistence, policy and supervision. Extensions are OS subprocesses speaking line-delimited JSON-RPC 2.0 over stdio, in any language ([guide](https://github.com/skaft-software/octet/blob/eb5d79e58ccba17c39d100d2398a53a8d6bd1c4b/docs/extensions.md#kernel-boundary)). This is the closest precedent for a Rust host with a broad reverse API. Rust embedders use crate hooks directly; the separate `octet-host` NDJSON embedding protocol never starts extensions ([SDK guide](https://github.com/skaft-software/octet/blob/eb5d79e58ccba17c39d100d2398a53a8d6bd1c4b/docs/sdk.md#octet-sdk-and-native-host)).
- **Breadth.** Static and dynamic tools, commands, prompt/context, hook interception, lifecycle observation, UI and input, session state and control, child agents, provider catalogs and streams, auth protocol records, host services and tool composition ([methods](https://github.com/skaft-software/octet/blob/eb5d79e58ccba17c39d100d2398a53a8d6bd1c4b/docs/extensions/API-0.4-REFERENCE.md#methods-and-terminal-semantics)). Availability is the intersection of manifest declaration, negotiated host offer and frontend binding. Auth records do **not** establish working extension OAuth: the concrete host returns unavailable; see [provider follow-up](#provider-follow-up-2026-11-16).
- **Protocol is not SDK.** The TS process SDK targets Node ≥ 22.19, is source-only (not registry-published), and documents missing dynamic tools, flags, remote UI, lifecycle subscriptions and several reverse services; its generator emits a machine-local launcher, not a portable bundle ([TS SDK](https://github.com/skaft-software/octet/blob/eb5d79e58ccba17c39d100d2398a53a8d6bd1c4b/sdk/typescript/process/README.md#handlers-and-explicit-limitations), [parity inventory](https://github.com/skaft-software/octet/blob/eb5d79e58ccba17c39d100d2398a53a8d6bd1c4b/sdk/conformance/sdk-parity.md)). Wire breadth is not author-facing parity.
- **Source-only qualification.** The protocol reference labels native model-turn hooks **not yet compiled or native-test-qualified** ([reference](https://github.com/skaft-software/octet/blob/eb5d79e58ccba17c39d100d2398a53a8d6bd1c4b/docs/extensions/PROTOCOL-REFERENCE.md#14b-native-model-turn-hooks-api-04-feature-session_entries)). Treat source contracts as design evidence, not shipped behavior.
- **Topology.** Default is one isolated process per binding. Opt-in modes include `oneshot`, `session`, `workspace_service`; workspace sharing requires manifest opt-in, the same workspace and trust partition, and a verified source digest ([lifecycle](https://github.com/skaft-software/octet/blob/eb5d79e58ccba17c39d100d2398a53a8d6bd1c4b/docs/extensions/legacy-authoring.md#runtime-lifecycle-and-sharing)).
- **Install.** A directory with `extension.toml`. The installer verifies paths and SHA-256 and stages the bundle, but runs no setup scripts and installs no dependencies: the author ships the runtime closure or requires a preinstalled interpreter.
- **Ownership fencing.** Session resources are keyed by host-issued `{session_id, extension_instance_id, process_generation}`; reverse calls normally require a live matching parent, with narrow explicitly permitted retained-owner exceptions. Late replies cannot restore authority. Reload sends the old generation's end before the new start; a crash replacement first gets an interrupted end. Dynamic catalog updates are transactional and frozen per request boundary ([registry](https://github.com/skaft-software/octet/blob/eb5d79e58ccba17c39d100d2398a53a8d6bd1c4b/crates/octet-agent/src/extension.rs#L869-L1083)).
- **Reentrancy.** Reverse calls are dispatched concurrently while the host awaits a reply, but bounded: composition only under a live tool parent, no recursive compaction, and a compaction request from a synchronous adapter queues until after the host reply.
- **Overrides.** `builtin_tool_overrides` names reviewed built-ins and does not inherit their effect, replay or concurrency privileges; other collisions are rejected ([manifest](https://github.com/skaft-software/octet/blob/eb5d79e58ccba17c39d100d2398a53a8d6bd1c4b/crates/octet-agent/src/extension_process/manifest.rs#L363-L381)).
- **Failures.** Explicit bounds: 1 MiB per line, 64 in flight, 30 s requests, 10 min tools, 2 s cooperative cancel grace, tombstones for late replies, process-group cleanup on shutdown ([bounds](https://github.com/skaft-software/octet/blob/eb5d79e58ccba17c39d100d2398a53a8d6bd1c4b/docs/extensions/API-0.4-REFERENCE.md#bounds)). Before-hooks fail closed; after-tool observation fails open with a diagnostic. Declared filesystem/network capabilities are consent metadata, **not a sandbox**; no CPU, memory, fd or PID quotas.

## Claude Code Mods

- **Shape.** Shipped JS/TS function-hook plugins (terminal 2.1.287+; some events later), distinct from MCP, settings hooks, skills, and the experimental model-authored Code Mode ([overview](https://code.claude.com/docs/en/plugins/mods/overview)). A plugin's `hooks/hooks.json` names one module exporting `register(on, options)`. Docs say mods run in Claude Code's own process; declarations mention worker respawn, but the thread or isolate topology is not public.
- **Constrained modules, not a sandbox, not npm.** Only static relative imports and the `claude-code` module; no `require`, dynamic import, bare npm packages, Node APIs or timers. External effects go through a mediated `$` (`$.fs`, `$.process`, `$.http`, …) that static analysis must be able to see ([constraints](https://code.claude.com/docs/en/plugins/mods/create#check-what-claude-code-reads-from-your-mod)). Permitted calls still run with the user's full authority, and `$.process.run` can start any executable. The restrictions buy analyzability, not isolation, and are Claude-specific product choices, not properties of TS extensions.
- **Middleware.** `on(event, matcher, ($, e, next) => …)`: first hook is outermost; `await next(e)` allows after-effects and result rewriting; returning without `next` short-circuits; calling `next` twice retries and can **duplicate side effects**. `next.origin` pins the caller's plugin and tier; `next.signal` and `next.budget` expose cancellation and time ([events](https://code.claude.com/docs/en/plugins/mods/events#how-a-hook-handles-an-event)). Every `$` method is itself a hookable event, so mods can intercept other mods' and the engine's calls.
- **Breadth.** Tool calls and permission verdicts, prompts, settings reads with source provenance, turns including streaming `turn.step` (model substitution or answering without a request), sessions and storage, subagents, commands and tools, independent model calls, UI. No custom provider or OAuth registration surfaced in docs or declarations (a search result, not proof of absence).
- **`engine.create`.** A per-load fold that can add whole namespaces to `$`; replacing an existing noun fails the plugin; organizational tiers can withhold ([declarations](https://github.com/anthropics/claude-code/blob/0cb75cebcdfd767ee14cd06295f9bf4163274e79/mods/types/claude-code.d.ts#L5368-L5382)). Its user-tier non-replacement rule is product policy, not a requirement for axo.
- **Install and ordering.** Marketplace or directory plugins with version caching and `/reload-plugins`; manifest `dependencies` are other plugins, not npm packages. Order is organizational prepend, user, organizational append, built-ins; a conditional managed guard (`sec-default`) can skip user hooks in managed sessions ([admin](https://code.claude.com/docs/en/plugins/mods/admin#know-what-happens-by-default)). Organizational authority is a product model, not a reason for axo to veto user overrides.
- **Failures.** Before `next`, a failing or timed-out hook is skipped; after `next`, its result is kept and effects are not repeated. `.catch` can fail closed. Most hooks have a 10 s own-execution budget (downstream `next` and most host calls excluded), 1 s for `.catch`, and about 1.5 s shared for session end ([failure](https://code.claude.com/docs/en/plugins/mods/events#handle-a-hook-that-fails), [limits](https://code.claude.com/docs/en/plugins/mods/reference#limits)). Denying after `next` cannot undo a completed tool. `$.store` read-modify-write across sessions is not atomic. `session.start` reruns on reload or worker respawn, not on `/clear`, `/resume` or `/branch`; module globals reset on reload.

## Goose: three surfaces

1. **External MCP servers** are Goose's advertised "extensions": tools, resources and prompts, in any language, installed by the server's own package manager (`uvx`, `npx`, …) ([guide](https://goose-docs.ai/docs/tutorials/custom-extensions/)). Stdio servers are spawned with the user's authority; no sandbox is established ([stdio](https://github.com/aaif-goose/goose/blob/2365bc5e898a38133c373eef2d1357416acd66e2/crates/goose/src/agents/extension_manager/stdio.rs#L13-L103)).
2. **Open Plugins** bundle skills, shell-command hooks (`sh -c` per invocation, JSON on stdin; only `PreToolUse` and `Stop` can block, neither rewrites) and, in current source but not yet the guide, stdio MCP servers ([hooks](https://goose-docs.ai/docs/guides/context-engineering/hooks), [plugin MCP](https://github.com/aaif-goose/goose/blob/2365bc5e898a38133c373eef2d1357416acd66e2/crates/goose/src/plugins/mcp_servers.rs#L12-L156)).
3. **In-process Rust platform extensions** get provider, session and scheduler managers directly ([context](https://github.com/aaif-goose/goose/blob/2365bc5e898a38133c373eef2d1357416acd66e2/crates/goose/src/agents/platform_extensions/mod.rs#L31-L230)). None of this privilege crosses MCP.

The reviewed MCP/plugin surfaces do not expose the platform tier's provider, provider-auth or general request-rewriting interfaces. Useful precedents: built-in MCP servers run in process over Tokio duplex streams ([builtin](https://github.com/aaif-goose/goose/blob/2365bc5e898a38133c373eef2d1357416acd66e2/crates/goose/src/agents/extension_manager/builtin.rs#L10-L38)); per-session selections are persisted and resolved into **leases**, so disabling an extension does not disturb in-flight calls, and processes stop when no lease holds them ([manager](https://github.com/aaif-goose/goose/blob/2365bc5e898a38133c373eef2d1357416acd66e2/crates/goose/src/agents/extension_manager/mod.rs#L765-L873)); enable starts the server before persisting the selection; tools carry host-assigned owner metadata. MCP cancellation is a cooperative notification; hook timeouts kill only the direct child.

## OpenCode V2

From the mutable `v2` branch and current docs; not claimed for any stable release.

- **Shape.** One npm package can export server, TUI, experimental GUI and optional RPC parts. The server part runs **inside** the OpenCode server with a Promise or Effect API ([overview](https://opencode.ai/docs/build/plugins), [loader](https://github.com/anomalyco/opencode/blob/v2/packages/core/src/plugin/module.ts#L88-L161)). The plugin `./rpc` export lets other plugins or external clients call plugin methods; it is a feature for clients, not the transport the plugin runs over ([RPC](https://opencode.ai/docs/build/plugins/rpc)).
- **Breadth.** Tools, tool interception, agents, commands, providers and model transforms, OAuth connection flows and credential resolution, session creation and control, permissions, shell, MCP catalog, per-plugin storage, VCS/worktree strategies ([server API](https://opencode.ai/docs/build/plugins/server)).
- **Install.** npm names and ranges, Git specs, local packages; exact versions and hashes stay pinned; missing packages install in the background ([plugins](https://opencode.ai/docs/plugins)).
- **Lifetime and order.** `setup` returns cleanup. Transforms are synchronous and **replayed in registration order** over fresh state on invalidation. Tool names resolve last-registration-wins; removing the later one reveals the earlier. A model request captures a stable tool snapshot. Reloads keep the unchanged activation prefix and tear down the changed suffix in reverse ([loader](https://github.com/anomalyco/opencode/blob/v2/packages/core/src/plugin.ts#L20-L167)). Provenance is per plugin (ID, path or package, status), not per field.
- **Durability.** Prompt-admission hooks edit a draft that becomes persisted input; context, compaction and title hooks rewrite outgoing requests without rewriting history. Duplicate concurrent submissions can run admission hooks twice.
- **Policy.** Managed policy is consulted before loading and some built-ins cannot be removed: host vetoes that axo's stated model does not have.

## Zed: a non-harness Wasm contrast

Zed is an editor; its API covers language servers, context servers, slash commands, debuggers and indexing ([guide](https://zed.dev/docs/extensions/developing-extensions), [trait](https://github.com/zed-industries/zed/blob/main/crates/extension_api/src/extension_api.rs#L67-L280)). Authors write Rust compiled to `wasm32-wasip2`; users download prebuilt archives without a compiler ([2024 rationale](https://zed.dev/blog/language-extensions-part-1), [install flow](https://zed.dev/blog/zed-decoded-extensions#installing-extensions)). Each extension gets its own Wasmtime store in process, with calls serialized per extension ([host](https://github.com/zed-industries/zed/blob/main/crates/extension_host/src/wasm_host.rs#L555-L762)). This is a real restricted guest boundary: WASI preopens only the extension's work directory, and process execution, downloads and npm installs go through capability checks ([granter](https://github.com/zed-industries/zed/blob/main/crates/extension_host/src/capability_granter.rs#L12-L86)). It is not a complete fault boundary: epoch interruption yields roughly every 100 ms but is not a per-call timeout or kill, and no per-extension memory limit was found. Servers it launches are ordinary native processes. Versioned WIT bindings keep old extensions working at a visible compatibility cost.

Zed shows prebuilt-artifact distribution and versioned ABI compatibility; it does not show that Wasm gives ergonomic, non-Rust harness parity.

## Cross-cutting findings

1. **Reach versus parity.** OMP, pi, OpenCode and Claude show broad single-language extension APIs. No reviewed system establishes parity with every Rust host avenue axo has. axo's acceptance criterion is public Rust parity **within extension contribution/session scope**, not binding host configuration, session storage, execution environments or supervision.
2. **In-process callbacks do not cross a process unchanged.** Function references, mutable shared inputs, UI component objects and synchronous return values need explicit RPC treatment: correlation, streaming, cancellation, host-owned handles and bounded reentrancy. Octet is the worked example of what that takes.
3. **Ownership is separate from trust.** A late callback from an old extension instance, generation or session must not affect a replacement (Octet's generation fencing, pi's context invalidation, Goose's leases, OpenCode's tool snapshots).
4. **Cancellation is not rollback.** Every system that times out a hook stops waiting; none undoes effects. Middleware retries (Claude's second `next`) and rerun boundaries (OMP's `before_agent_start`) can repeat external effects. Durable effects need explicit operation identity and replay rules.
5. **Collision policy is per registry everywhere.** First-wins, last-wins, replaceable defaults and hardcoded host winners coexist inside one system. Provenance (`sourceInfo`, `next.origin`, owner metadata) is common; a uniform, user-forceable override rule is not.
6. **Composition styles differ.** Ordered typed transforms with chained results (pi, OMP, OpenCode replay) versus general around-middleware (Claude). Around-middleware makes after-effects, short-circuiting and stream forwarding explicit, with ordering and replay hazards; this is not a reason to redesign already-supported Rust operations for TS.
7. **Installers own dependencies or push them onto users.** OMP, pi and OpenCode resolve npm/git dependencies themselves (OMP with its own embedded Bun). Octet and Goose MCP make the author or user supply interpreters and closures; Claude forbids bare dependencies. The [Bun standalone executable](https://bun.sh/docs/compiler/executables) docs show a runtime can ship inside an executable, while native addons and dynamically loaded dependencies still need packaging care.
8. **Headless is a different UI matrix.** OMP, pi, Claude and Octet all degrade or reject UI calls in headless modes (secret prompts, custom components, confirmations). Mode capability must be explicit, not inferred from a `hasUI` flag.

Supplemental sources: [JSON-RPC 2.0](https://www.jsonrpc.org/specification) defines framing and correlation only, not streaming, cancellation, lifecycle or reentrancy. [`deno_core`'s architecture notes](https://github.com/denoland/deno_core/blob/main/ARCHITECTURE.md) show V8 embedding with sync and async Rust ops, without a complete application runtime.

## Provider follow-up (2026-11-16)

This is source evidence, not live-provider testing. The original snapshots above remain unchanged. This follow-up reads newer pi [`1f6f319`](https://github.com/earendil-works/pi/tree/1f6f319bb28992a40b99c147fffb23b65a23129d), OMP [`bf9a9fb`](https://github.com/can1357/oh-my-pi/tree/bf9a9fbd40e96766d528a9f19a603e53e8c0b5a1), OpenCode **v1** [`ae92f315`](https://github.com/anomalyco/opencode/tree/ae92f3158f2c3a44d25ad3ba8855a366d681e617), and the same Octet snapshot. OpenCode v1 auth hooks must not be conflated with the mutable V2 survey above.

### Authentication and request ownership

- **pi:** complete native providers implement `login`, `refresh`, and `toAuth`, returning key, headers and base URL ([auth types](https://github.com/earendil-works/pi/blob/1f6f319bb28992a40b99c147fffb23b65a23129d/packages/ai/src/auth/types.ts)). At this newer snapshot, `registerProvider(name, config)` is legacy compatibility, not the preferred new-provider API. Its OAuth callbacks include `onAuth`, `onDeviceCode`, `onPrompt`, `onSelect`, optional progress/manual code and an abort signal ([callbacks](https://github.com/earendil-works/pi/blob/1f6f319bb28992a40b99c147fffb23b65a23129d/packages/ai/src/compat/extension-oauth-types.ts)). The host owns credential persistence and refresh: under five minutes remaining, recheck under the credential-store lock and persist before unlocking ([resolve](https://github.com/earendil-works/pi/blob/1f6f319bb28992a40b99c147fffb23b65a23129d/packages/ai/src/auth/resolve.ts#L106-L189)). Runtime provider replacement and unregister restore built-in behavior ([custom providers](https://github.com/earendil-works/pi/blob/1f6f319bb28992a40b99c147fffb23b65a23129d/packages/coding-agent/docs/custom-provider.md#L19-L143)).
- **OMP:** extension OAuth still supplies `login`, optional `refreshToken`, `getApiKey` and `modifyModels`, rather than pi's newer native interface ([config](https://github.com/can1357/oh-my-pi/blob/bf9a9fbd40e96766d528a9f19a603e53e8c0b5a1/packages/coding-agent/src/extensibility/extensions/types.ts#L2269-L2348)). Host-managed refresh uses a 60-second skew, single-flight, database leases and compare-and-swap persistence—not pi's five-minute policy ([refresh](https://github.com/can1357/oh-my-pi/blob/bf9a9fbd40e96766d528a9f19a603e53e8c0b5a1/packages/ai/src/auth/refresh.ts)). Unregister removes runtime auth/state and reloads static models ([registry](https://github.com/can1357/oh-my-pi/blob/bf9a9fbd40e96766d528a9f19a603e53e8c0b5a1/packages/coding-agent/src/config/model-registry.ts#L3995-L4093)). Both systems show host-owned refresh/storage, though their APIs and account handling differ.
- **OpenCode v1:** an auth hook declares login methods and a loader; the loader returns constructor options including executable `fetch` ([types](https://github.com/anomalyco/opencode/blob/ae92f3158f2c3a44d25ad3ba8855a366d681e617/packages/plugin/src/index.ts)). OAuth returns a URL/instructions plus automatic or manual-code callback. The host stores credentials, but the plugin owns refresh timing and writes updates via `client.auth.set`; custom fetch owns the HTTP call and can adapt responses as well as requests. This is broader than axo's agreed request-only rewrite.
- **Octet's concrete gap:** runtime `providers/register`, update and unregister exist, and the wire declares `provider/auth/request` with authorize/refresh/revoke actions. Yet the [coding-host policy](https://github.com/skaft-software/octet/blob/eb5d79e58ccba17c39d100d2398a53a8d6bd1c4b/crates/octet-coding-agent/src/extensions/provider_runtime.rs#L388-L406) returns `unavailable` (or `revoked` for revoke), with no lease; proxy registration requires `auth.kind == "none"`. No complete extension login UI/storage/refresh lifecycle was found. Native subscription login is a different surface. The [Pi adapter](https://github.com/skaft-software/octet/blob/eb5d79e58ccba17c39d100d2398a53a8d6bd1c4b/extensions/octet-pi-compat/lib/custom-provider.mjs#L77-L99) can shape key/headers/base URL, but that is not host-managed extension OAuth. Its [HTTP delegation](https://github.com/skaft-software/octet/blob/eb5d79e58ccba17c39d100d2398a53a8d6bd1c4b/crates/octet-agent/src/extension_process/native_provider/custom_http.rs) makes the extension perform HTTP while Rust decodes bytes. The [TS helper allowlist](https://github.com/skaft-software/octet/blob/eb5d79e58ccba17c39d100d2398a53a8d6bd1c4b/sdk/typescript/process/index.d.mts#L11-L15) does not expose provider/auth registration; protocol breadth is not SDK parity. [Qualification warnings](https://github.com/skaft-software/octet/blob/eb5d79e58ccba17c39d100d2398a53a8d6bd1c4b/docs/extensions.md#L430-L449) explicitly prevent treating source schemas as live-provider qualification.

These implementations motivate distinct levels: **1**, login/refresh/credential-to-auth; **2**, rewrite Rust's URL/headers/body before Rust sends and parses; **3**, extension-owned HTTP with Rust decoding; and fully custom normalized streaming. Levels 1 and 2 are the approved priority. Request rewrite is sufficient to express the agreed level-2 contract, **not proof that every subscription provider fits it**: response translation or a different wire protocol may require a later level. `ApiKind` stays closed. pi's newer source also removed Gemini CLI/Antigravity while OMP retained them ([pi changelog](https://github.com/earendil-works/pi/blob/1f6f319bb28992a40b99c147fffb23b65a23129d/packages/ai/CHANGELOG.md#L1345)); provider availability is version-sensitive.

Declarative endpoint/key/model configuration alone does not supply arbitrary interactive OAuth or executable refresh. It can select existing auth logic (pi's `oauth: "radius"` is one exception), and command helpers can outsource credentials, but neither is evidence of generic provider plugin parity. Live subscription compatibility must be proved by actual login, refresh and inference, not inferred from these sources.

## Approved direction (2026-11-16)

These are decisions for future implementation, not survey findings:

- **Scope and ownership:** the bridge and TS SDK live in axo's repository and use only its public Rust API. Add a missing shared Rust seam rather than a TS-only capability. Extensions contribute named tools, schemes, prompt sections, definitions and providers, and operate inside sessions (messages, branch-scoped custom state, children and events). They do not replace `SessionStore`, `ConfigSource`, `CredentialStore`, the default `Streamer`, `Supervision` or `ExecEnv`; create/open/fork/shutdown/navigate sessions; change project trust; or answer/dismiss host questions and accept/revise mode results.
- **Composition:** the bridge owns wholesale setters such as `set_tools` and policy/spawn-hook lists, composing host and per-extension contributions. The user's ordered enabled list decides collisions, with winning provenance diagnostics; `call`, `yield`, and `artifact`/`file`/`tool` remain reserved. Registered code commands join the common command catalog after built-ins and modes, before skills; hosts keep `commands` / `parse_command` / `run_command`.
- **Runtime and files:** trusted TS/JS on host-supplied Bun, with one supervised process per extension and explicit user grouping, no Workers. axo bundles no Bun. Each extension receives a host-chosen data directory; keeping files there is convention, not enforcement. Extensions add no settings keys; axo owns only its user-only enabled-list/grouping key. See [placement and failure decisions](bun-topology.md#settled-direction), including the crash budget, visible failures without replay/fallback, and process/group—not exact allocation—memory accounting.
- **Providers:** generic Rust `login`/`refresh`/credential-to-`ModelAuth`, host credential storage and locked refresh, typed host-rendered login interactions (URL, device code, text, select, progress, cancel), reversible runtime provider/model registration, and level-2 request rewrite. Unregister restores the prior registration. Closed wire formats stay Rust-owned; additional subscription integrations live in extensions, while existing built-in Codex is migrated to the shared contract. A missing required provider fails naming its extension, never silently bypasses its hook.
- **Deferred:** level 3 and custom streaming; the general extension-to-host UI/lifecycle request channel; MCP adapter and `ast_edit`. Typed login interaction does not depend on that general channel. Preserve existing session boundaries, replay classes and fail-closed policy semantics rather than adding universal middleware.

### Delivery phases

This living-documentation alignment happens **now, before Phase 1**, not as a Phase 1 task. Each implementation phase requires its own detailed plan; see Track 5 in [`plan.md`](../plan.md).

1. **Rust provider/login seam:** no Bun. Generic login/refresh/auth shaping, typed interaction, reversible runtime models/providers and level-2 hook; migrate Codex and Axome callers. Prove offline registration/login/refresh/request rewrite and retain Codex login.
2. **Bridge and TS providers:** supervised processes, optional grouping, minimal manifest, host inputs, correlated bidirectional protocol, cancellation/streaming and generation fencing. Choose transport against `ProcessSupervisor`'s actual stdin behavior. Prove a Claude-subscription extension kept outside axo logs in, refreshes and streams in Axome; killing it visibly fails in-flight work, restarts it and its descendants are cleaned up; three failures disable it with a host event. Source research alone does not satisfy this proof.
3. **Session capabilities and commands:** tools, policies, spawn hooks, schemes, prompt sections, definitions, messages/custom state/events and registered commands; shared Rust changes and bridge-owned composition. Preserve request boundaries, child/fork inheritance and `Replay::Never` defaults.
4. **Packaging/install:** host-triggered add/update installation with the host's Bun, SDK compatibility diagnostics, prebundled no-install option and process/group memory reporting. No default cap; optional limits only if a real need emerges.

Phase 2 depends on Phase 1; Phases 3 and 4 depend on Phase 2 and are independent of each other. No axo extension-runtime memory or latency was measured: the placement figures are standalone Bun probes.

## Remaining detailed-plan questions

- Exact protocol/transport, manifest and install API shapes, compatibility checks and synchronous-return seams need concrete phase plans—not a reopened topology choice.
- General UI/lifecycle channel design remains pinned for later; login has its own typed interaction.
- Cross-extension ordering in external harnesses beyond cited paths, Claude's internal topology/crash replay, and Goose's live plugin-MCP incorporation remain unqualified. They do not determine axo's settled collision rule.
