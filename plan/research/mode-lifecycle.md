# Session modes: lifecycle, subagents, model precedence, and shell enforcement

## Scope and evidence

Read-only survey of official documentation and upstream source. **Implementations are not interchangeable:** OpenCode V1 and V2 differ, and current Kilo is an OpenCode-derived CLI/backend plus frontend, not merely the old Roo-derived extension. Source snapshots: Codex `rust-v0.167.0`; omp `98eacbbc8d1b98eb6582302f407c647c0fb38f6e`; OpenCode V1 files at the individually linked revisions, V2 plan plugin `2670273ff17da96f85c5826ced57aa1b368754fa`; Kilo `b6a49d01c10d7e26c42a8a14b3441b7a1856c04c`; Roo `b867ec9145750d0ae1ff7f02d35406e9bf2a0b16`; Gemini `6f926425248c74d340ad472f77beb3590bf55b15`. Claude runtime internals are not public source here; claims below use official docs. Bracketed identifiers resolve to URL + actual file path in Sources.

## 1. Exit, entry, approval, continuation, and plan storage

| System | Model-facing transition and arguments | User decision, continuation, manual control, artifact |
|---|---|---|
| **Claude Code** | `EnterPlanMode` enters without a permission prompt; `ExitPlanMode` asks approval. Official hook docs say model input is **typically empty**; runtime injects `plan` and `planFilePath` read from disk before hooks run. Exact closed-runtime JSON schema is **not verified**; do not confuse hook-enriched input with model arguments. [C1,C2] | Approval: **Yes, and use auto mode** (fallback **auto-accept edits**; or **BYPASS PERMISSIONS** if enabled), **Yes, manually approve edits**, **No, keep planning** with feedback. Acceptance changes permission mode and starts editing; rejection stays planning. `Ctrl+G` edits plan. `showClearContextOnPlanAccept` adds approve-and-clear-context option. `Shift+Tab` leaves without approving; `/plan` enters for a prompt; startup flag/defaultMode supported. Default plan files **`~/.claude/plans`**, configurable project-relative `plansDirectory`. [C1,C3] |
| **Codex CLI** | **No enter/exit tool in inspected mode interface.** User selects `/plan`, `Shift+Tab`, or host collaboration-mode mask. Model completes a `<proposed_plan>…</proposed_plan>` block, not an `update_plan` call; that checklist tool is rejected during Plan. [D1,D2] | Inspected prompt tells model not to ask “should I proceed?”: user switches out of Plan and requests implementation. No Claude-style acceptance/context-clear workflow was found in the inspected source. Transcript retained; plan is inline rollout/TUI `ProposedPlanCell`, not a required disk artifact. Mode changes deliver updated developer instructions. [D2,D3] |
| **omp** | Current snapshot uses **`write {path:"xd://propose", content:"<slug>"}`**, not an exit tool with plan text: slug matches **`local://<slug>-plan.md`**. Submission dispatches to plan-proposal handler, which requires active plan state. Older `resolve action:apply` examples are obsolete for this snapshot. No model-enter tool verified. [O1,O2] | Review: **Approve and execute** (fresh session), **Approve and compact context**, **Approve and keep context**, **Refine plan**, **Save and quit**. Approval clears mode, restores tools, optionally autosaves, queues execution prompt containing approved plan. Refine/dismiss stays planning. Save copies plan to chosen path, starts new session. `/plan` while active confirms if draft exists, interrupts turn, restores execution state and journals **paused**; another no-arg `/plan` fully disables, retaining draft. Compaction cancellation is special: mode exited but execution not auto-dispatched. [O2,O3] |
| **OpenCode V1** | `plan_exit({})` calls `question.ask` with **Yes: switch to build and start implementing** / **No: stay plan and refine**. No plan body/path argument; computes session plan path. [P1] | Yes appends synthetic **user** message `agent:"build"`, text “The plan at … has been approved, you can now edit files. Execute the plan”; No rejects tool. No context clear in this path. Manual primary-agent switching is separate. Plan path generated by `Session.plan`, historically `.opencode/plans/<timestamp>-<slug>.md` with global-data fallback outside Git. [P1,P2] |
| **OpenCode V2** | **No model exit tool in inspected plugin.** Reminder explicitly says remain Plan until **user switches agents**, and tell user to switch if implementation requested. [P3] | User agent switch appends enter/leave reminder without clearing history. Default plan is **conversation**, not file: “Do not create or update plan files unless user explicitly asks”; requested files only **`~/.opencode/plan/`**. Plugin reconciles reminders after compaction/revert. [P3] |
| **Kilo current CLI + frontend** | `plan_exit({path?:string})` validates a real written plan through `PlanFile.locate`; returns metadata `{plan}` and “Ending planning turn.” **Tool itself neither approves nor switches agents.** Frontend/backend followup owns transition. [K1] | `PlanFollowup.ask`: **Start new session** creates `code` session with LLM handover/todos; **Continue here** appends “Implement the plan above.” as `code`, selects code model; **Keep refining** appends planning instruction; custom text continues under `plan`; dismiss stops. Manual agent picker/Tab also switches. Git plans **`.kilo/plans/<timestamp>-<slug>.md`**; non-Git under XDG data `kilo/plans`. [K2,K3] |
| **Roo Code** | `switch_mode({mode_slug,reason?})` proposes any configured target mode; `new_task({mode,message,todos?})` starts a child task in target mode. Architect is planning mode, not a separate binary permission overlay. [R1,R2] | Mode switch asks approval unless configured auto-approved; rejection leaves mode. Accepted switch retains task conversation, updates mode, waits 500ms before continuing. User can switch in mode picker. Architect instructions use `update_todo_list`, markdown plan if unavailable; suggest `/plans` for saved file, not mandatory hidden plan artifact. No dedicated clear-context plan approval shown. [R1,R3] |
| **Gemini CLI** | `enter_plan_mode({reason?})` asks interactively; `exit_plan_mode({plan_filename})` reviews stored plan. In pinned implementation filename is reduced with `basename`, resolved **inside designated plans directory**, checked against symlink escape; not an arbitrary project path. [G1,G2] | **Automatically accept edits** → AUTO_EDIT; **manually accept edits** → DEFAULT; reject feedback/Cancel stays PLAN. Tool returns approved path and instruction to implement; no context clear. Policy-allowed noninteractive exit defaults to YOLO; interactive allowed-without-dialog exit defaults DEFAULT. Manual `/plan`, approval-mode flag and `Shift+Tab`. Default **`~/.gemini/tmp/<project>/<session>/plans`**, configurable plan directory. [G2,G3] |

## 2. Subagents while planning

| System | Spawn availability, inherited restrictions, configuration/use case |
|---|---|
| **Claude Code** | Agent/Task delegation available; built-in **Plan** is read-only research; **Explore** is read-only search. **Parent Plan forces child Plan irrespective of child's `permissionMode`**; exception: agent-team teammate rules. `dontAsk` additionally denies actions that would prompt. Configure `tools`, `disallowedTools`, model and permissionMode; Agent deny rules can disable delegation/types. Purpose: separate exploration context while root plans; not limited solely to agents named Plan/Explore. [C4] |
| **Codex** | `spawn_agent` available when multi-agent feature enabled. Child inherits parent approval policy/reviewer, cwd, and permission-profile snapshot. **Does not inherit Plan collaboration mode as a hard restriction**: spawned configuration initializes its own session (Default in inspected path), not a blanket read-only child. Role config can reduce features/tools, not elevate parent authority. Thus parent Plan guidance is not equivalent to OS-enforced read-only delegation. [D4,D5; child Default conclusion partly implementation tracing, not a documented product guarantee] |
| **omp** | Task available and parallel exploration/critique explicitly encouraged. Shared child creation forcibly rewrites **every agent** to tools **read, grep, glob, web_search**, adding ast_grep only if originally declared; prepends planning instructions, clears spawns/prewalk. `restrictToolNames` disables MCP. Custom eval tools and isolation/apply/merge rejected; bundled seance hidden/rejected. Parent spawn-policy and disabled-agent settings still gate choices. This is actual whitelist enforcement, not just prompt instruction. [O2,O4] |
| **OpenCode V1/V2** | `task` gated by caller's `permission.task` and selected subagent config. Historical V1 `deriveSubagentSessionPermission` copied parent **session deny** rules; do not mistake that for guaranteed inheritance of primary Plan agent's own restrictions. Subsequent upstream cutover removed **parent-agent deny inheritance** so children use their own agent permissions. V2 Plan reminder forbids asking children to modify files, but that sentence is guidance; configure allowed subagents/child permissions for an enforced read-only workflow. Each child may specify own model/tools/permissions. [P3,P4,P5] |
| **Kilo current** | `task` allowed per caller permissions. Deliberately differs from upstream: **native Plan edit denials and session edit denials are descendant ceilings**; notebook/MCP restrictions retained. Broad delegator bash deny/allowlist guards **not inherited**; child's own bash policy governs shell. Custom delegator's edit policy is not automatically imposed on children. Do not claim full root Plan shell-policy inheritance. [K4] |
| **Roo Code** | `new_task`/`switch_mode` always-available tools, including Architect. Child is separate task in explicitly requested mode, parent paused and resumed after completion; **not forced Architect/read-only**. Can therefore delegate Code implementation subject to subtask approval. Mode tool groups are configurable; built-in Architect's local edit restriction does not automatically turn requested Code children into read-only children. [R1,R2,R3] |
| **Gemini CLI** | Default Plan policy permits named research agents **codebase_investigator** and **cli_help**, catch-all denies other tools/agents absent stronger policy. Local children have own tool registry (declared tools, otherwise inheritance), agent tools removed to prevent recursive spawning, and calls still pass scheduler policy with subagent identifier; user/admin policy can customize. Purpose: codebase investigation/help without implementation. [G4,G5] |

## 3. Model precedence and restoration after explicit changes

| System | What wins on entry and during mode? What happens on exit if user changed model? |
|---|---|
| **Claude Code** | Session `/model` selects active alias/model (startup precedence separately documented). **`opusplan` is a model alias**, not intrinsic model for every Plan session: Opus while Plan, Sonnet while executing. Replacing alias through `/model <specific-model>` changes session model, rather than establishing a saved pre-Plan stack. **[INFERENCE]** if explicit choice replaces opusplan, exit does not resurrect that discarded alias. Some automatic plan upgrades depend on selected model/allowlist; do not generalize “Plan always Opus.” [C5] |
| **Codex** | Built-in Plan mask has **model:null**, effort **Medium**; Default mask also no model. `apply_mask` retains selected model for absent field; explicit user model therefore survives entering/leaving. No pre-Plan model stack. Host-supplied mask **with model** explicitly changes it; not a universal `/model > any future mode transition` rule. Changed model is communicated through separate developer **`<model_switch>`** instructions; collaboration mode has its own developer fragment. [D1,D6,D7] |
| **omp** | Entry resolves **plan role**, captures pre-Plan model/thinking **once**, applies temporary model; changing role live re-applies it without replacing saved pre-Plan state. Exit restores saved state even if current differs. **[INFERENCE from restore code]** ordinary explicit mid-Plan model choice is undone on exit. Resume preserves restored journal model instead of reapplying current role. Approval execution-tier slider, when offered, defaults to default role and is applied **after restore**, so selected execution tier wins. Compaction-failure branch intentionally keeps plan model. [O3,O5] |
| **OpenCode V1** | Agent model config and manual selection exist, but inspected **plan_exit specifically copies last user message model** into synthetic Build message, falling back provider default; it does **not** look up Build's configured model. Therefore exit tool can retain planning model regardless of intended per-agent default. Do not extrapolate this to every manual switch/UI revision. [P1] |
| **OpenCode V2** | Core agent and model selection are independent; switching primary agent does not update session model column. Inspected TUI preserves active model/variant across agent switch. Thus explicit model changed while Plan persists when leaving; no automatic pre-Plan restoration. Subagents differ: own configured model, otherwise caller model. [P6,P7] |
| **Kilo current** | Official custom-agent docs describe per-agent manual choice > agent model > default, with switching back restoring that agent's choice. Model state persists per agent in `model.json`; workflow-specific overrides can precede saved state. Plan acceptance's Continue-here path explicitly calls `setAgentModel` for **code**, rather than blindly preserving Plan model. A Plan-specific manual change belongs to Plan; leaving selects Code's saved/configured model, switching back recovers Plan choice. [K2,K5] |
| **Roo Code** | Mode has saved API profile (provider+model etc.). Manual profile activation persists it for current mode; switching loads target mode's saved configured profile, or saves current as target default if none. Switching back restores the updated original-mode choice, **not original entry snapshot**. **`lockApiConfigAcrossModes`** overrides sticky switching and keeps current config across modes. [R4] |
| **Gemini CLI** | Automatic plan routing applies only to **auto** model: planning Pro, approved implementation Flash, configurable `general.plan.modelRouting`. Explicit `/model`/launch model bypasses auto routing, so changed explicit model survives exit. This is phase routing, not a pre-Plan snapshot restore. Subagent model selection separately configurable; do not conflate root phase routing and child model defaults. [G3,G6] |

## 4. Shell in “read-only” modes

| System | Shell available? Actual enforcement and caveats |
|---|---|
| **Claude Code** | **Yes.** Current official order: interactive terminal with bypass available → neither classifier nor prompt for planning commands; otherwise auto available + `useAutoModeDuringPlan` (default on) → classifier approves/blocks; otherwise commands beyond built-in read-only set prompt, **even sandbox auto-allow**. Optional Bash sandbox is separate defense (Seatbelt macOS, bubblewrap Linux/WSL2), not synonymous with Plan and not an assurance that all approved commands are read-only. [C1,C6] |
| **Codex** | **Yes. Plan does NOT switch sandbox to read-only.** Mutation prohibition is primarily mode instructions; permission profile/approval policy remain independently selected. An explicitly read-only sandbox can enforce filesystem restrictions; workspace-write can permit workspace mutations even during Plan. OS mechanisms and tool approval machinery exist, but must not be credited to Plan automatically. [D1,D2,D8] |
| **omp** | Root retains enabled bash; inspected `bash.ts` and approval middleware have no Plan-specific guard. Root shell nonmutation therefore **[INFERENCE bounded to inspected execution paths] prompt-only**, not a demonstrated allowlist/sandbox. Built-in write/edit independently enforce canonical local-sandbox-only writes and forbid delete/rename. **Children have no bash tool at all** due fixed whitelist. [O2,O3,O4,O6] |
| **OpenCode V1** | At inspected native-agent revision defaults `* allow`; Plan overrides edit but **not bash**. Thus no built-in Plan command allowlist in that snapshot: shell obeys user's permission config, while planning prompt says read/inspect only. User can configure e.g. bash `* ask` and `git diff* allow`; generic command parsing/permission matching is not a built-in readonly classifier or OS sandbox. [P8] |
| **OpenCode V2** | Official docs explicitly: Plan **“Does not restrict shell commands. They follow your permission config.”** Plugin restricts edit/write/patch to plan directory, not shell. Therefore read-only applies incompletely unless host/user config constrains bash; no mode-specific OS sandbox established by inspected code. [P3,P9] |
| **Kilo current** | **Yes, allowlisted.** Built-in readOnlyBash policy denies broad writes and shell operators (redirection/substitution/chaining/pipes), allows selected inspection commands; runtime parses command blocks and checks permissions. User-configurable allow/ask/deny patterns. Not an OS sandbox. Important bypass seam: native Plan edit deny propagates to children, but **root bash guards do not**—a child can have broader own bash policy. [K4,K6] |
| **Roo Code** | Built-in **Architect has no command group** (`read`, `.md`-restricted edit, `mcp` only), so native execute_command is **unavailable**, not a read-only command classifier. Custom modes can add command group; those commands then follow ordinary approval/allow-deny mechanisms in user's terminal. MCP is still permitted; “no native shell” does not mean every external side effect is impossible. [R3,R5] |
| **Gemini CLI** | **Default blocks shell entirely**, including git status/diff: pinned plan.toml catch-all deny **priority 60**, read-only tools/agents exceptions 70; run_shell_command is not an exception. Plan markdown writes separately allowed. Higher-tier user/admin policies can allow chosen commands; therefore default enforcement is policy-engine denial, not immutable sandbox. Optional OS/container sandbox is independent. [G4,G7] |

## Design-relevant conclusions (inference, not upstream requirements)

1. **Exit proposal, approval, transition, and execution dispatch are separate operations.** Kilo makes this especially visible: tool only finalizes; followup decides fresh vs same-session execution. omp/Claude add context policies to approval.
2. **Subagent inheritance needs an explicit contract.** Claude forces Plan inheritance; omp whitelists child tools; Gemini gates named research agents; OpenCode guidance is weaker; Kilo inherits edit but not shell restrictions; Codex collaboration Plan is not a permissions ceiling.
3. **Choose model restoration policy explicitly.** Snapshot restore (omp), per-mode sticky choice (Roo/Kilo), session-sticky selection (OpenCode V2/Codex), and phase routing (Claude opusplan/Gemini auto) give different results after user model changes.
4. **“Read-only mode” is not one enforcement mechanism.** Native-tool denial, command permission rules, classifier review, OS isolation, and model instructions protect different boundaries; several surveyed defaults do not prevent shell mutation.
