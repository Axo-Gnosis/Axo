# Sessions, Durability & Compaction

`axo` persists every session as an append-only JSONL entry tree (`crates/axo/src/store/` and `crates/axo/src/session/`), journals background jobs into the same file (`crates/axo/src/jobs/`), and maintains context size through recoverable artifact elision and model summaries (`crates/axo/src/compaction/`).

## Session Storage (`JsonlStore` & `SessionStore`)

The host passes the store to `Axo::builder(models, store)`. The bundled `JsonlStore::new(root)` stores sessions under `<root>/--<encoded-cwd>--/<timestamp>_<uuidv7>.jsonl`, where `root` is whatever directory the host chooses, `<encoded-cwd>` is the absolute cwd without its leading separator, with `/`, `\`, and `:` replaced by `-`, and the timestamp replaces `:` and `.` with `-`.

- **Configuration sampling:** `Axo::create_session`, `Axo::open_session`, and `Axo::schemes` each call `EffectiveConfig::resolve` once: `ConfigSource::user` first, then `ConfigSource::project(cwd)` only when the effective project access (`SessionOptions::project_access`, else the user layer's `project` policy from that same sample) is `Read` or `Trust`. The session keeps the resulting `EffectiveConfig` (access, settings, prompt overrides, skill roots, context files) for its lifetime; a host edit takes effect on the next create or open. An invalid layer fails the call with `Error::Config` naming the layer's `origin`. `defaultModel` resolves (`EffectiveConfig::default_model`) only when a session falls back to it, so an unresolvable value fails only that selection.
- **Lazy file creation:** `Axo::create_session` reserves a planned path and `Header` in memory. The first submission, non-system message, or `child_start` creates the file and parent directory, flushing earlier buffered metadata. Child and fork files are created immediately because their headers link to a parent. A built-in command that only changes model or thinking settings does not by itself create a new session file.
- **Single-writer lock:** Opening an existing session for writing (`JsonlStore::open_write`) acquires an exclusive non-blocking OS file lock (`std::fs::File::try_lock`) on the session file itself. The lock is explicitly released when the last local writer/write-operation handle drops, so briefly inherited subprocess descriptors cannot prolong it after writer closure. A second writer receives `Error::SessionBusy`. Read-only opens (`Axo::open_session_read`, `Axo::list_sessions`, and `Axo::schemes`, which reads only the header) take no lock.
- **Torn-line repair:** If the final line lacks a trailing newline, `open_write` appends the newline when the line parses as JSON, and otherwise truncates the torn line back to the previous complete line.
- **Sequence numbers (`SeqEntry`):** Every entry loaded or appended receives a 0-based monotonic `seq: u64` corresponding to its line index after the `Header`.
- **Synced records:** `Entry::requires_sync` identifies `run_start`, `run_end`, `job_start`, `child_start`, `job_end`, and any `message` carrying a non-empty `admittedJobs` or `deliveredJobs` receipt. Every `SessionWriter::append` implementation must complete durable storage for these entries before returning, so job state survives a host crash. The bundled JSONL writer flushes every line and additionally calls `sync_data` for these records.

### The session journal (`crates/axo/src/session/journal.rs`)

Every entry an open session writes goes through one journal task that alone owns the session's `SessionWriter`. Callers queue an append and await its result; readers (`attach`, `fork`, context reads, maintenance preparation) take an immutable snapshot of the entries, ids, projection and revision, which never waits on a write in flight.

- **Batches:** An append is a batch of entries sequenced together with nothing interleaved. The journal completes each entry's base: a fresh id (or the id the caller chose, when the entry's content already names it; a taken id fails the batch with `Error::ContextChanged`), and the current position as parent, each entry parented on the one before. `leaf` and `branch_summary` keep their target as parent. A write that fails keeps the entries before it (they are durable) and fails the call.
- **Publication order:** The snapshot and the `SessionEvent::Entry` broadcasts follow the disk, one event per entry in append order. Appends complete in the order they were queued.
- **Revision:** Every entry except `submission`, `usage`, `model_change` and `thinking_level_change` bumps the session's revision. Compaction, `/shake`, automatic clearing and branch summaries prepare from a snapshot and commit only if the revision is unchanged (`Error::ContextChanged` otherwise; compaction retries up to three times). A `job_start`, `child_start`, or `job_end` landing meanwhile counts as a change.
- **Owner:** The session (a run, standalone maintenance, or a non-summarizing `navigate`) is claimed by an atomic compare-and-set, so `prompt` sees `Error::Busy` exactly while something else owns it; a prompt whose `request_id` is being submitted concurrently gets that submission as `PromptResult::Duplicate`. Every mutating `Session` call finishes its write and what follows on its own task, so dropping its future never leaves the session half-changed.
- **Close:** Dropping the session closes an idle writer at once, so the file lock is free for the next `open_session`.

### JSONL format (`FORMAT_VERSION = 1`)

Line 1 is the `Header` (`{"type":"session","version":1,"id":"…","timestamp":"…","cwd":"…","parentSession":…,"forkedFrom":…}`). A child additionally has `spawn: SpawnLink`: the parent's session id, optional spawning call id, depth, optional catalog agent and model selector, and the resolved spec after child defaults and spawn hooks. JSON uses camelCase field names. Host spawns have no call id; an inherited live model has no selector. The child's `parentSession` names the parent file and `forkedFrom` is absent. Root and fork headers have no spawn link. Subsequent lines are `Entry` variants sharing `EntryBase { id, parent_id, timestamp }`:

| `type` | Variant | Role in projection |
| :--- | :--- | :--- |
| `message` | `Entry::Message { base, message, submission_id, admitted_jobs, delivered_jobs }` | Appends `AgentMessage` (`System`, `User`, `Assistant`, `ToolResult`, or `Custom`). `admittedJobs` names job rows; `deliveredJobs` names individual messages of those rows. Both are omitted when empty, never enter model context, and are [delivery receipts](#background-job-durability) |
| `thinking_level_change` | `Entry::ThinkingLevelChange { base, thinking_level }` | Updates `Projection::thinking` |
| `model_change` | `Entry::ModelChange { base, provider, model_id }` | Updates `Projection::model` (`"{provider}/{model_id}"`) |
| `usage` | `Entry::Usage { base, kind, provider, model, usage, note }` | Recorded for accounting (such as summary requests); never enters model context |
| `compaction` | `Entry::Compaction { base, summary, first_kept_entry_id, preserved_user_ids, tokens_before, details, usage, from_hook, reason, focus, system_message }` | Replaces messages before `first_kept_entry_id` with the checkpoint `system_message`, preserved user messages, and a `compactionSummary` custom message wrapping the summary in `<summary>…</summary>` (lowered to a user message). `reason` (`CompactionReason`: `manual`, `threshold`, or `overflow`; absent in older files) records what started it and `focus` the user's focus for a manual compaction |
| `branch_summary` | `Entry::BranchSummary { base, from_id, summary, details, usage, from_hook, focus }` | Injects a `branchSummary` custom message wrapping the summary in `<summary>…</summary>` (lowered to a user message); `focus` records the user's focus for the summary |
| `custom` | `Entry::Custom { base, custom_type, data }` | Host metadata appended with `Session::append_custom`; `Session::custom` returns the latest value of that type on the current root-to-leaf path (branch-scoped). Never enters model context |
| `custom_message` | `Entry::CustomMessage { base, custom_type, content, details, display }` | Lowered to a user message in model requests |
| `context_edit` | `Entry::ContextEdit { base, target_id, replacement }` | Replaces `target_id`'s content (`Some(ContextReplacement)`) or hides `target_id` from the projection (`None`) |
| `label` | `Entry::Label { base, target_id, label }` | Dormant format type: pi's label lines are parsed and preserved, but axo has no label API. Not projected and never enters model context |
| `session_info` | `Entry::SessionInfo { base, name }` | Written by `Session::set_name`; `Session::name` returns the latest name in file order, globally rather than branch-scoped. Not projected and never enters model context |
| `leaf` | `Entry::Leaf { base }` | Moves the active branch pointer to `base.parent_id` (`None` = before the first entry) |
| `run_start` | `Entry::RunStart { base, run_id }` | Marks the start of an agent run |
| `run_end` | `Entry::RunEnd { base, run_id, outcome, reason }` | Marks a settled run (`done`, `aborted`, `failed`, `interrupted`; a parked run is `interrupted` with `reason: "restart_limit"`) |
| `run_resumed` | `Entry::RunResumed { base, run_id, attempt }` | Records a crash recovery resume attempt |
| `submission` | `Entry::Submission { base, submission_id, kind, parts, request_id }` | Durable `prompt`, `steer`, or `follow_up` input recorded before queueing. `parts` holds the prepared [prompt parts](prompts-and-context.md#prompt-parts-cratesaxosrcinputrs) as sent (`Saved` instead of `Content`, skill commands unexpanded); the model-facing text lives on the user `message` entry. Older files wrote `content` (text blocks); it loads through `#[serde(alias = "content")]` as `Text` parts. Built-in commands write no submission |
| `job_start` | `Entry::JobStart { base, session_id, job_id, call_id, command, artifact }` | Written in one batch with, and immediately before, the tool result of the call that started job `job_id` (`bg_N`): the `bash` result that promoted it, or the foreground result of a command that exited leaving helpers running in its container (such a record is never admitted; it only reserves the id). `session_id` is the session that started it (copied records in a fork keep the parent's id); `artifact` is the job's output spool `artifact://<artifact>`. Never enters model context; foreground commands whose container is empty at exit write no job records |
| `child_start` | `Entry::ChildStart { base, session_id, job_id, call_id, child_session_id, child_path, agent, model }` | Creates a child's persistent parent-registry row (`agent_N`). Records the parent id, child id and path, optional catalog agent, and expanded model. Host spawns omit `call_id` and this entry itself admits the row. Tool spawns record `callId`; their `spawn` result's `admittedJobs` receipt admits the row. Never enters model context |
| `job_end` | `Entry::JobEnd { base, job_id, text, is_error, partial, run_id }` | One row message: a command result or child-run report. `job_id` names message 1 as the row alone and later messages as &lt;row&gt;/&lt;n&gt; (n ≥ 2). JSON `partial` is omitted when false; `runId` is omitted when absent and identifies the reported child run when present. Command JSON is unchanged. Never enters model context; the model sees text only through its delivery message |
| *(unknown)* | `Entry::Unknown(Value)` | Preserved verbatim on load; ignored by projection |

`Session::set_name` and `Session::append_custom` may append at any time, including during a run; neither adds model-context messages. Names have newlines replaced with spaces and are trimmed; an empty name becomes `None`. An empty custom type is rejected with `Error::InvalidInput`. A latest custom entry with no data makes `Session::custom` return `None`.

## Projection (`crates/axo/src/store/project.rs`)

`project(entries, leaf)` walks the ancestor chain from the current leaf (`None` uses the last entry in the file; an `Entry::Leaf` moves the leaf to its `parent_id`) back to the root:

1. **Latest compaction boundary:** If the root-to-leaf path contains one or more `Entry::Compaction` entries, projection starts from the last compaction's `system_message` snapshot and `compactionSummary` custom message, emits its `preserved_user_ids` in path order, and then replays entries from `first_kept_entry_id` onward.
2. **Branch summaries:** Any `Entry::BranchSummary` on the active segment becomes a `branchSummary` custom message (lowered to a user message).
3. **`ContextEdit` application:** On the active path, the last `Entry::ContextEdit` targeting an entry ID wins. `replacement: None` removes that message from the projection (used to hide transient-error or overflow turns); `Some(ContextReplacement)` replaces its content blocks (used by `/shake` and automatic clearing) and zeroes provider token usage on assistant messages positioned before the last `context_edit` or `compaction` on the path.
4. **Incremental caching (`Projection::apply`):** `Session` maintains the projection incrementally as entries are appended, rebuilding from scratch only when navigating or when an edit/compaction invalidates earlier entries.

## Crash Recovery (`crates/axo/src/recovery.rs`)

When `Axo::open_session` opens a session file, `plan_recovery` inspects the journal and projection without filesystem access. `Session` applies the plan and attaches any available command-output artifacts:

- **Unfinished tool calls:** If the last assistant message on the path has tool calls without matching `ToolResult` entries:
  - Tools with `Replay::Never` (`bash`, `edit`, and `write` to a scheme whose `write_replay` is `Never`) immediately receive a persisted synthetic `ToolResult` with `is_error: true` explaining that the process stopped before completion. `Session` points to any partial command output as `artifact://<n>`, backed by `<session>/artifacts/<n>.<tool>.<escaped-call-id>.log`.
  - Under `RecoveryPolicy::Resume` (default), tools with `Replay::Safe` (`read`, `grep`, `find`, `ask`, `wait`, `spawn`, `yield`, and `write` to a plain path or `local://`) are left unanswered so `Agent::continue_run` re-executes them in the background. A repeated `spawn` call adopts its existing child by call id.
  - Under `RecoveryPolicy::MarkInterrupted`, `Replay::Safe` calls also receive interrupted results, unconsumed submissions are not requeued, and `Entry::RunEnd { outcome: Interrupted }` is appended immediately.
- **Interrupted or failed assistant responses:**
  - If the last assistant response stopped with `StopReason::Length` and had tool calls, every unanswered call receives a truncated-output error result and the run continues.
  - If the last assistant response had a context-overflow signal on a `Stop` reply without tool calls, recovery keeps the reply and closes the run `done` if its maintenance checkpoint already committed (otherwise re-running maintenance). A retryable provider error or overflow with a failed turn hides the failed assistant turn with `Entry::ContextEdit { replacement: None }` and resumes the run.
  - A non-retryable failed or aborted response with unanswered tool calls gets not-executed (or `Operation aborted`) results before the run closes `Failed`/`Aborted`.
- **Unconsumed submissions:** Any `Entry::Submission` saved after the last `RunEnd` (or during an open run) whose `submission_id` has not yet been consumed by an `Entry::Message` is requeued in order (`Steer`, `FollowUp`, or starting a new `Prompt` run). Requeued messages are rendered again from the stored `parts`: a skill command is expanded from the current `SKILL.md`, and a saved image is re-read from `local://`.
- **Restart loop cap (`RESTART_LIMIT = 5`):** If a run accumulates 5 `Entry::RunResumed` markers in a row without an intervening `Entry::Message`, recovery appends `Entry::RunEnd { outcome: Interrupted, reason: "restart_limit" }` and stops resuming it.
- **Interrupted background commands:** Before recovery, every command job of this session that was admitted but has no `job_end` receives one (`is_error: true`): `Command was interrupted when the session closed; it may have partially run. Output so far: artifact://<n>` (or `… Its output is unavailable.` when the spool file is gone). The result becomes pending delivery; see [Background Job Durability](#background-job-durability). Child runs instead recover from their own journals.

## Attaching, Navigating & Forking (`Session`)

- **`session.attach(from_seq)`:** Snapshots `Attach { missed, live, events }` from one point of the append order without waiting on a write in flight. Entries publish and live run state relays under the locks `attach` holds while subscribing, so every `SessionEvent::Entry` and live update lands either in the snapshot or on the receiver, never both and never neither. Agent events that follow a write (such as `MessageEnd` after its `message` entry) may still arrive for an entry already in `missed`:
  - `missed`: all `SeqEntry` items with `seq > from_seq` (or all entries when `from_seq` is `None`).
  - `live`: `LiveSnapshot` containing `run_id`, active `maintenance` (`Compact`, `Shake`, `BranchSummary`), and flattened run fields: `running`, partial `streaming` message, `pending_tool_calls`, `queued_steering`, and `queued_follow_up`; plus projected `messages`, `pending_questions`, and `jobs` (`Vec<JobInfo>`). `Session` owns live run state and event delivery; queue contents come from `Agent::queued()`.
  - `events`: a `tokio::sync::broadcast::Receiver<SessionEvent>`. If a slow receiver lags, it can call `session.attach(Some(last_seen_seq))` to catch up without stalling the agent loop.
- **`session.navigate(target, NavigateOptions { summarize, focus })`:**
  - Appends `Entry::Leaf { base: EntryBase { parent_id: target, .. } }`, records `ModelChange` / `ThinkingLevelChange` if the live selection differs from the target branch's historical selection, restores the file ledger and nested context tracker to the new projection, and updates the agent's transcript.
  - Running command jobs and children keep running. Their messages are delivered on whichever branch is selected when they finish; delivery names the originating command or child agent.
  - With `summarize: true`, first summarizes the abandoned branch with a separate tool-free request (the `BRANCH_SUMMARY` prompt, plus the [focus](#focus) when given) and appends `Entry::BranchSummary` at `target` in place of the `leaf` entry. `focus` without `summarize` returns `Error::InvalidInput`.
- **`session.fork(entry_id)`:** The fork inherits the parent's `EffectiveConfig` and ordered `ToolHooks` from `SessionOptions::tool_hooks`, and never calls the `ConfigSource`.
  - Copies the root-to-`entry_id` ancestor chain into a new session file whose `Header` records `parent_session` and `forked_from`.
  - Copies the parent's side files into the fork's session directory: `artifacts/` (hard-linked read-only, copy fallback) and `local/` (copied), so `artifact://` and `local://` URLs, including saved prompt content, resolve in the fork. The output spool of a job that is still running (or retaining helpers) is never hard-linked: the fork gets a read-only snapshot copy, so later output appended by the parent's job does not show up in the fork. Copying is best effort; an entry that cannot be carried over is logged and skipped.
  - The fork gets its own empty job registry: no running command handles or child rows carry over, and copied `job_start` / `child_start` records of the parent's session are ignored (their `session_id` differs). Each namespace numbers from one past the highest raw record or receipt naming it.
  - If `entry_id` is a user message, `fork` copies up to that user message's parent and returns `Fork::editable: Option<Vec<PromptPart>>` so a client can prefill its editor, chips included: the parts of the `submission` that produced the message, or, for a message without one (older sessions), one `Text` part joining its text blocks. The returned parts can be resubmitted as-is (`Saved` parts resolve to the copied `local://` files). Any open run on the copied path is closed with `RunEnd { outcome: Interrupted, reason: Some("fork") }` (a run whose last response already settled it is closed with that outcome instead).

## Background Job Durability

A `bash` call promoted to the background (see [Background Jobs](prompts-and-context.md#background-jobs-cratesaxosrcjobsrs) for the model-facing behavior) is tracked by the session's `JobRegistry` and journaled so its result reaches the transcript **exactly once**, across navigation, crashes, and reopen.

- **Admission:** The promoted tool result carries `admittedJobs: ["bg_N"]` and is written in one batch with the job's `job_start`, the start first, so a receipt never names a job whose start is not on disk. A job becomes deliverable only once that batch commits; a `job_start` whose receipt never committed is ignored. A retained `job_start`, written with the foreground result of a command that exits leaving helpers running, has no receipt either: on reopen it is not a job, but its `bg_N` is counted so the id stays reserved. Tools never write journal entries themselves.
- **Result:** When the job's root command ends, its result is stored at once (`proc://` shows it). Its `job_end` is appended as soon as the command has ended and its admitting batch has committed, by whichever happens second; then the result becomes pending. So `job_end` always follows its `job_start` and receipt, and a job whose receipt never committed writes no `job_end`. A job ending while the session shuts down writes no `job_end`; reopen reconciles it as interrupted. A failed `job_end` write is logged, and the result still becomes pending in memory; a persistent journal failure then surfaces through the next receipt-bearing message write.
- **Delivery receipt:** A pending result is reserved for exactly one message: a `wait` tool result, or a `job_result` custom message (`Background job results:` …). That message's entry carries `deliveredJobs: ["bg_N", …]`. Only a committed entry consumes the result: if the write fails, or the reserving message is a synthetic result (aborted or never-executed `wait`), the reservation is released and the result is delivered again later. Delivery is counted at transcript commit, not at provider acceptance: once committed, the result is part of the transcript, and a later failed or retried provider request never resends it as a new message.
- **Raw reconstruction:** On open, the registry is rebuilt from **all raw entries** of the file, not the projected branch, so receipts on abandoned branches still count. For each `job_start` of this session: admitted and delivered → done; admitted and ended but not delivered → pending; admitted and not ended → reconciled as interrupted (see [Crash Recovery](#crash-recovery-cratesaxosrcrecoveryrs)). Command and child ids have separate counters, each one past the highest name in any raw `job_start`, `child_start`, `job_end`, admission receipt, or delivery receipt, so an id the model has seen is never reused. A second open finds the `job_end` and writes nothing.
- **No wake on open:** Opening a session never starts a model run for pending or interrupted results. They reach the model with the next prompt (ahead of the user's message), at the steering point of a run that recovery resumes, or through `wait`.
- **Root result vs. retained helpers:** A command's result is its root shell's: it returns once the root exits plus a fixed 100 ms output drain. Descendants still alive in the command's container stay supervised as `bg_N` with status `helpers running`, keep writing to the same spool, and can be inspected or killed through `proc://`. Their later exit never produces a second result or delivery (see [Background Jobs](prompts-and-context.md#background-jobs-cratesaxosrcjobsrs)).
- **Idle wake:** When a pending result appears while the session is idle (no run, no maintenance), `Session` starts a run whose prompt is the `job_result` message. During a run, results are injected at the next turn boundary, after the current tool batch; they never count as a steer.
- **Stop latch:** `Session::abort` stops only the current turn and its foreground command; background jobs keep running. If a run was active, the Stop latches automatic continuation off. The latch is also set when a run settles with any outcome other than `Done` (error, abort, interruption, persist or journal failure). While latched, finished results stay pending instead of waking the session; the next `prompt`, `steer`, or `follow_up` clears the latch and carries them. A Stop while idle sets nothing.
- **Shutdown:** `Session::shutdown` cancels and waits for the active run, recursively shuts down live children, then stops every open command job and awaits its task. Dropping a `Session` kills its command containers and releases its table-owned child handles; independently held child handles can remain live. Cleanup reaches what the selected container tracks: process-group mode cannot see descendants that called `setsid`, and both modes are best effort if the session process dies without running shutdown.

## Child sessions

`Session::spawn` and the model's `spawn` tool create a separate durable session and start its first prompt asynchronously. A child is not a fork: it starts with its own prompt and transcript, and its header's `SpawnLink` persists the resolved `AgentSpec`, including defaults, output schema, and spawn-hook replacements. Revival uses that spec rather than reloading its catalog definition. `SessionInfo::spawn` exposes the link in session listings; `Session::agent` exposes it on a live child. See [Spawning child sessions](extending.md#spawning-child-sessions) for the host API and [Spawning and returning results](prompts-and-context.md#spawning-and-returning-results) for the model tools.

### Rows, run messages, and delivery

- **One row per child:** The parent's `JobRegistry` gives each child one `agent_N` row for its lifetime. Each settled child run adds a message to that row; later prompts do not allocate a new row. A command has only its single result.
- **Admission and replay:** Host spawns are admitted by `child_start`. Tool spawns write `child_start` with `callId` when the child is created, then admit it only when the `spawn` result commits `admittedJobs: ["agent_N"]`. Child messages completed before admission are held, neither journaled to the parent nor delivered until admission commits. Failed admission aborts the live child. On reopen, unadmitted tool rows remain pending and hidden; rerunning the same safe call adopts the same `agent_N` and child file, reconciles its journal, and admits it through the rerun's result. If recovery marks that call interrupted instead, its child stays dormant.
- **Message references:** Message 1 is named by its row alone; later messages append a slash and a canonical decimal sequence number starting at 2. `job_end` and `deliveredJobs` use these message references, while `admittedJobs` names rows. Delivered text still labels each result with the row, not the sequence number.
- **Run outcome:** Without an output schema, a successful run reports its last non-empty assistant text, joining text blocks with newlines, or “(no text output)”. Failed, aborted, and interrupted runs report their failure/stop reason instead. With an output schema, an accepted `yield` supplies the result (raw text for strings, compact JSON otherwise); an unyielded answer or failed run is an error with the last rejected attempt or last answer, while abort/interruption retains its stop report. The parent receives one `job_end` per child run, deduplicated by `runId`; a task that fails before starting a run reports a startup error without a run id.
- **Exactly-once delivery:** Child messages use the same durable reservation and delivery receipts as command results, through `wait` or a `job_result` message. The row label is the catalog agent name or “subagent”. A failed child-message journal write removes the in-memory message so reopen can derive it again from the child's journal. A committed receipt consumes only that message, not the child row.
- **Parent reopen:** After registering the parent's registry, open reads each admitted child's journal and reconciles its completed runs, deduplicating reports already present in the parent. Pending tool-spawned children are reconciled only when their spawning call reruns. It revives children with unfinished runs or unconsumed submissions under `RecoveryPolicy::Resume`; settled children are registered as parked. Messages discovered during reconciliation do **not** wake the parent: they wait for its next prompt, a resumed run's steering point, or `wait`. A revived child that finishes later follows normal live delivery and can wake an idle parent unless the Stop latch is set.
- **Delivered text:** Child results are capped at 2000 lines / 50 KB with a pointer to the full latest result at `agent://agent_N/result`; an oversized first line becomes a notice suggesting that URL or a JSON pointer. Command and child deliveries escape axo's fixed wrapper tags, but `job_end` keeps full, unescaped text. The latest result and projected child transcript remain readable through [agent URLs](prompts-and-context.md#agent) after delivery.

### Budgets and lifecycle

- **Turn budget:** Each new or resumed child run resets its request counter. At `maxTurns`, calls other than `yield` are blocked with “turn budget exhausted” without changing the tool list. If that turn contains tool calls, a `turn_budget` custom message asks for a final answer stating completed work, remaining work, and hand-off needs, or tells an output child to call `yield` with its best final result. Other calls in the following wrap-up request are blocked with `terminate: true`, ending the run; a text-only answer ends normally for a child without an output schema. A run containing the wrap-up notice reports `partial: true`, and delivery adds “(partial: turn budget exhausted)” to its label. An answer that finishes before needing the notice is not marked partial.
- **Concurrent runs:** All descendants of one root share `subagents.maxConcurrent` FIFO run slots; a child holds its slot for the whole run, including tool waits. Root runs do not take slots. With nested spawning enabled, children waiting for descendants can exhaust all slots and deadlock; the limit does not release slots during `wait`.
- **Parking and revival:** An idle child with no maintenance, open jobs, or pending job messages releases the session table's strong handle. External `Arc<Session>` handles keep it live; otherwise its writer can close. `Axo::session` returns an existing live handle or revives a known parked child from its journal, recorded model/thinking selection, and persisted spec. It does not start a new prompt for a settled child.
- **Follow-ups:** `Session::follow_up` queues input until an active run would otherwise finish, and starts a run immediately on an idle session. Input arriving after the last drain point starts the next run. `write agent://agent_N` uses the same path after reviving a parked child, and its reply becomes another message on the existing row.
- **Stop and shutdown:** Stopping the parent does not stop children. `Session::kill_job` on a child row aborts that child's current run. Parent `shutdown` recursively shuts down live children without writing a terminal `run_end` for shutdown-cancelled runs, so reopening the parent resumes them. Dropping a parent releases its owned child handles; a child retained independently by the host can finish while the parent is closed, and its report is reconciled on reopen.

## Manual `/shake` (`Session::shake`)

`session.shake(mode)` shrinks projected context without calling a model. It is also the [built-in command](prompts-and-context.md#user-commands-cratesaxosrccommandsrs) `/shake <mode>` (`elide`, `images`, or `thinking`; `ShakeMode` serializes lowercase). Maintenance emits `SessionEvent::MaintenanceStart` and `SessionEvent::MaintenanceEnd`, and returns `Error::Busy` while a turn or maintenance is running (`Error::MaintenanceAborted` if cancelled):

| `ShakeMode` | Behavior |
| :--- | :--- |
| `ShakeMode::Elide` | Outside the newest `4,000` tokens, replaces tool-result text blocks and fenced/XML blocks in user or assistant text of `>= 400` tokens with `[shaken ~N tokens; full text: artifact://<n>]`, writing the original text to `<session>/artifacts/<n>.shake.txt` first. Skill spans (`<skill …>…</skill>`), `SKILL.md` read results, system messages, compaction summaries, and tool-call arguments are never touched |
| `ShakeMode::Images` | Replaces every `UserBlock::Image` in user, tool-result, and custom messages (except messages containing a skill span) with `[shaken image; full image: artifact://<n>]`, writing the decoded image bytes to `<session>/artifacts/<n>.shake.<ext>` |
| `ShakeMode::Thinking` | Replaces each `AssistantBlock::Thinking` with `[shaken thinking; full thinking: artifact://<n>]`, saving that block's JSON to `<session>/artifacts/<n>.shake.json` (skipped in messages containing a skill span) |

Each modified message receives one `Entry::ContextEdit`. Because edits are append-only, navigating to the entry before the shake restores the unshaken view.

## Manual Compaction & Focus (`Session::compact`)

`session.compact(focus)` (the built-in command `/compact [focus…]`) runs a summary checkpoint right away, without checking the automatic trigger and even with `compaction.enabled: false`. It never takes the clearing shortcut, so it always asks the model for a summary (live or separate per `compaction.summaryRequest`), and commits an `Entry::Compaction` with `reason: manual`.

### Focus

`focus` is the user's plain-text direction for what a summary should prioritize (`/compact keep the auth decisions; drop the exploratory logs`). It goes after the format template in every summary request of that pass (the first or update checkpoint, a split turn's prefix, or a branch summary), outside the `<conversation>` and `<previous-summary>` data tags, because it is an instruction rather than data:

```text
Focus from the user: <focus>
Give it priority, but keep every section of the format.
```

The focus is saved on the committed entry's `focus` field. Automatic and overflow compaction never have one.

## Automatic Compaction (`crates/axo/src/compaction/`)

### Window and trigger math (`Limits::resolve`)

```text
W           = min(model.context_window, compaction.max_context)
reply       = min(model.max_tokens, 32_768)
reserve     = compaction.reserve_tokens.unwrap_or(min(reply + 4_096, W / 4))
trigger     = W - reserve
keep_recent = compaction.keep_recent_tokens.unwrap_or(min(20_000, trigger / 4))
```

Context tokens are estimated from the latest non-errored assistant message's provider-reported usage plus local token estimates (`(utf16_units * 2).div_ceil(7)`, `4,800` per image) for messages after it, falling back to full local estimation when an edit invalidates earlier usage.

Automatic maintenance checks `estimate > trigger` in `prepare_request` (before a prompt and between tool turns) and in `finish_turn` (after a turn settles).

### One action per pass: clearing vs summarization

When `estimate > trigger`, `axo` evaluates two candidates locally:

1. **Recoverable clearing (`elide::prepare`):** Protects the newest `40,000` tokens of tool-result content and elides older eligible tool-result text into `<session>/artifacts/<n>.shake.txt` markers (`[shaken ~N tokens; full text: artifact://<n>]`). Clearing is chosen **only** if the resulting context estimate is at most `trigger - 20,000`, and is skipped when `trigger < 20,000`.
2. **Checkpoint summarization (`Entry::Compaction`):**
   - **Cut point:** Walks backward from the end of the transcript accumulating `keep_recent` tokens and cuts at the first valid boundary (`User`, `Custom`, or `Assistant`, never a `ToolResult`). Message-less records just before the cut (`run_start`, `submission`, `run_end`, settings changes) stay with the kept tail; a cut at a `User` or `Custom` message is always a complete-turn boundary, so only history is summarized. If a single turn exceeds the budget, the turn is split at an `Assistant` boundary and its prefix is summarized with the `COMPACTION_SPLIT_TURN` prompt and merged with the history summary.
   - **Live summary (`SummaryRequest::Live`):** Appends the summary prompt to the live uncleared conversation with `ToolChoice::None` so the request reuses the provider's prompt cache. If the response contains a tool call, stops with `Length` / `Error` / `Aborted`, is empty, or is not strictly smaller than the messages it replaces, it is rejected and `axo` falls back to a separate summary request.
   - **Separate summary (`SummaryRequest::Separate`):** Serializes the messages to summarize into `<conversation>` text and sends a tool-free request under the `SUMMARY` prompt.
   - **Carryover:** The committed `Entry::Compaction` stores the current `SystemMessage` snapshot, `preserved_user_ids` (recent whole user messages from the summarized region that fit within `keep_recent`), `details: {"readFiles": […], "modifiedFiles": […]}`, and the summary text. File lists come from successful `read`, `write`, and `edit` results and use absolute paths.
   - **Escalation bound:** Automatic maintenance attempts one clearing attempt, then at most 3 summary attempts (falling back to a separate request after a failure) before failing with `Error::Compaction`.

## Transient Retry & Overflow Recovery

- **Transient retry:** `axo_ai::is_retryable_error` and `axo_ai::is_fatal_error` classify provider errors; `axo::RetrySettings` owns turn and summary retry policy. When a turn ends with a retryable provider error (`HTTP 429`, `500`, `502`, `503`, `504`, `520`, `524`, stream transport errors, or `overloaded`/`rate_limit`/`too many requests`/`service_unavailable`/`server_error` without quota exhaustion), `Session` hides the failed assistant message with `Entry::ContextEdit { replacement: None }`, emits `SessionEvent::Retry { attempt, delay_ms }`, sleeps, and retries within `retry.maxRetries`. Defaults are 3 retries with 2/4/8-second exponential delays; a server delay hint replaces the backoff, but a hint above `retry.maxDelayMs` (default 60,000 ms) stops retries. `retry.baseDelayMs` sets the backoff base, `retry.maxRetries: 0` disables retries, and an unrepresentable backoff stops retries.
- **Fixed transport retries:** before a response body is consumed, `axo_ai` separately allows 2 request-level retries. This transport detail is not controlled by `RetrySettings`; it honors server delays up to 60 seconds. A longer hint returns the failed response without sleeping so the adapter preserves the hint for the configurable turn-level policy.
- **One-shot overflow recovery (`axo_ai::is_context_overflow`, `axo_ai::is_recoverable_length`):** When a turn fails with context overflow (or stops with `StopReason::Length` when output is 0 and input + cache_read >= 99% of context window, or output is below requested max_tokens) and `compaction.enabled` is `true`, `Session` hides the failed turn and any tool results it produced, runs recoverable clearing followed by a separate-request compaction pass if needed, and retries once within the same run.
