# Sessions, Durability & Compaction

`axo` persists every session as an append-only JSONL entry tree (`crates/axo/src/store/` and `crates/axo/src/session/`), journals background jobs into the same file (`crates/axo/src/jobs/`), and maintains context size through recoverable artifact elision and model summaries (`crates/axo/src/compaction/`).

## Session Storage (`JsonlStore` & `SessionStore`)

The host passes the store to `Axo::builder(models, store)`. The bundled `JsonlStore::new(root)` stores sessions under `<root>/--<encoded-cwd>--/<timestamp>_<uuidv7>.jsonl`, where `root` is whatever directory the host chooses, `<encoded-cwd>` is the absolute cwd without its leading separator, with `/`, `\`, and `:` replaced by `-`, and the timestamp replaces `:` and `.` with `-`.

- **Configuration sampling:** Each `create_session`, `open_session`, and `Axo::schemes` call samples configuration once through `EffectiveConfig::resolve` and keeps the result for the session's lifetime; see [Evaluation](configuration.md#evaluation-effectiveconfigresolve).
- **Lazy file creation:** `Axo::create_session` reserves a planned path and `Header` in memory. The first submission, non-system message, or `child_start` creates the file and parent directory, flushing earlier buffered metadata. Fork files are created immediately because their header names `parentSession`; a child's file is created by its first `submission`, which is written before the parent's `child_start`. Model, thinking, persona (`agent_change`), and mode (`mode_change`) selection metadata do not by themselves create a new session file.
- **Single-writer lock:** Opening an existing session for writing (`JsonlStore::open_write`) acquires an exclusive non-blocking OS file lock (`std::fs::File::try_lock`) on the session file itself. The lock is explicitly released when the last local writer/write-operation handle drops, so briefly inherited subprocess descriptors cannot prolong it after writer closure. A second writer receives `Error::SessionBusy`. Read-only opens (`Axo::open_session_read`, `Axo::list_sessions`, and `Axo::schemes`, which reads only the header) take no lock.
- **Torn-line repair:** If the final line lacks a trailing newline, `open_write` appends the newline when the line parses as JSON, and otherwise truncates the torn line back to the previous complete line.
- **Sequence numbers (`SeqEntry`):** Every entry loaded or appended receives a 0-based monotonic `seq: u64` corresponding to its line index after the `Header`.
- **Synced records:** `Entry::requires_sync` identifies `run_start`, `run_end`, `job_start`, `child_start`, `job_end`, and any `message` carrying a non-empty `admittedJobs` or `deliveredJobs` receipt. Every `SessionWriter::append` implementation must complete durable storage for these entries before returning, so job state survives a host crash. The bundled JSONL writer flushes every line and additionally calls `sync_data` for these records.

`Axo::open_session` rejects a child file with `Error::ChildSession { path, root }`. The optional root path is found by following persisted parent ids through the store's session listing; it is absent if the listing fails or that ancestry cannot be resolved. Open that root with the host's own session options, then call `Axo::session(child_id)` to access or revive the child. `Axo::open_session_read` remains available for unlocked read-only child access. Store listings include children as well as roots.

### The session journal (`crates/axo/src/session/journal.rs`)

Every entry an open session writes goes through one journal task that alone owns the session's `SessionWriter`. Callers queue an append and await its result; readers (`attach`, `fork`, context reads, maintenance preparation) take an immutable snapshot of the entries, ids, projection and revision, which never waits on a write in flight.

- **Batches:** An append is a batch of entries sequenced together with nothing interleaved. The journal completes each entry's base: a fresh id (or the id the caller chose, when the entry's content already names it; a taken id fails the batch with `Error::ContextChanged`), and the current position as parent, each entry parented on the one before. `leaf` and `branch_summary` keep their target as parent. A write that fails keeps the entries before it (they are durable) and fails the call.
- **Publication order:** The snapshot and the `SessionEvent::Entry` broadcasts follow the disk, one event per entry in append order. Appends complete in the order they were queued.
- **Revision:** Every entry except `submission`, `usage`, `model_change`, `thinking_level_change`, `agent_change`, and `mode_change` bumps the session's revision. Compaction, `/shake`, automatic clearing and branch summaries prepare from a snapshot and commit only if the revision is unchanged (`Error::ContextChanged` otherwise; compaction makes up to three summary attempts in total). A `job_start`, `child_start`, or `job_end` landing meanwhile counts as a change.
- **Owner:** The session (a run, standalone maintenance, or a non-summarizing `navigate`) is claimed by an atomic compare-and-set, so `prompt` sees `Error::Busy` exactly while something else owns it; a prompt whose `request_id` is being submitted concurrently gets that submission as `PromptResult::Duplicate`. Every mutating `Session` call finishes its write and what follows on its own task, so dropping its future never leaves the session half-changed.
- **Close:** Dropping the session closes an idle writer at once, so the file lock is free for the next `open_session`.

### JSONL format (`FORMAT_VERSION = 1`)

Line 1 is the `Header` (`{"type":"session","version":1,"id":"…","timestamp":"…","cwd":"…","parentSession":…,"forkedFrom":…}`). A child additionally has `spawn: SpawnLink`: the parent's session id, optional spawning call id, depth, optional catalog agent and model selector, and the resolved spec after child defaults and spawn hooks. JSON uses camelCase field names. Host spawns have no call id; an inherited live model has no selector. A child's header has no `parentSession` or `forkedFrom`; its parent is `spawn.parentSessionId`. Root and fork headers have no spawn link. Subsequent lines are `Entry` variants sharing `EntryBase { id, parent_id, timestamp }`:

For a team member, `SpawnLink::team` is a `TeamLink` containing the per-parent id, member name, optional catalog team name, charter, optional brief, and ordered `roster: Vec<RosterEntry>`. Each roster entry has a name, description and session id. The persisted link fixes messaging routes and the team prompt across revival. Non-team children omit it.

| `type` | Variant | Role in projection |
| :--- | :--- | :--- |
| `message` | `Entry::Message { base, message, submission_id, admitted_jobs, delivered_jobs }` | Appends `AgentMessage` (`System`, `User`, `Assistant`, `ToolResult`, or `Custom`). `admittedJobs` names job rows; `deliveredJobs` names individual messages of those rows. Both are omitted when empty, never enter model context, and are [delivery receipts](#background-job-durability) |
| `thinking_level_change` | `Entry::ThinkingLevelChange { base, thinking_level }` | Updates `Projection::thinking` |
| `model_change` | `Entry::ModelChange { base, provider, model_id }` | Updates `Projection::model` (`"{provider}/{model_id}"`) |
| `agent_change` | `Entry::AgentChange { base, agent }` | Updates `Projection::agent` to the root persona's catalog name; absent `agent` removes the persona. Children never write it: their persona is the spec in their spawn link. Never enters model context |
| `mode_change` | `Entry::ModeChange { base, mode, restore }` | Updates branch-scoped `Projection::mode` and `Projection::mode_restore`; absent mode ends the mode. Optional `ModeRestore { provider, model_id, thinking_level }` saves the selection to restore on exit. Neither field enters model context |
| `usage` | `Entry::Usage { base, kind, provider, model, usage, note }` | Usage of summary requests that did not commit (`kind`: `compaction` or `branch_summary`; `note`: the error). Committed summaries carry usage on their own entry. Never enters model context |
| `compaction` | `Entry::Compaction { base, summary, first_kept_entry_id, preserved_user_ids, tokens_before, details, usage, from_hook, reason, focus, system_message }` | Replaces messages before `first_kept_entry_id` with the checkpoint `system_message`, preserved user messages, and a `compactionSummary` custom message wrapping the summary in `<summary>…</summary>` (lowered to a user message). `reason` (`CompactionReason`: `manual`, `threshold`, or `overflow`; absent in older files) records what started it and `focus` the user's focus for a manual compaction |
| `branch_summary` | `Entry::BranchSummary { base, from_id, summary, details, usage, from_hook, focus }` | Injects a `branchSummary` custom message wrapping the summary in `<summary>…</summary>` (lowered to a user message); `focus` records the user's focus for the summary |
| `custom` | `Entry::Custom { base, custom_type, data }` | Host metadata appended with `Session::append_custom`; `Session::custom` returns the latest value of that type on the current root-to-leaf path (branch-scoped). Never enters model context |
| `custom_message` | `Entry::CustomMessage { base, custom_type, content, details, display }` | Lowered to a user message in model requests |
| `context_edit` | `Entry::ContextEdit { base, target_id, replacement }` | Replaces `target_id`'s content (`Some(ContextReplacement)`) or hides `target_id` from the projection (`None`) |
| `label` | `Entry::Label { base, target_id, label }` | Dormant format type: pi's label lines are parsed and preserved, but axo has no label API. Not projected and never enters model context |
| `session_info` | `Entry::SessionInfo { base, name }` | Written by `Session::set_name`; `Session::name` returns the latest name in file order, globally rather than branch-scoped. Not projected and never enters model context |
| `leaf` | `Entry::Leaf { base }` | Moves the active branch pointer to `base.parent_id` (`None` = before the first entry) |
| `run_start` | `Entry::RunStart { base, run_id }` | Marks the start of an agent run |
| `run_end` | `Entry::RunEnd { base, run_id, outcome, reason, usage, queued }` | Marks a settled run (`done`, `aborted`, `failed`, `interrupted`; a parked run is `interrupted` with `reason: "restart_limit"`). Optional `usage` sums the run's persisted assistant usage, including failed responses, but not maintenance or child spend. `queued` lists the submission ids still waiting in the steering, follow-up, mail and quiet queues when the run ended (empty when a fork or `RecoveryPolicy::MarkInterrupted` drops them) |
| `run_resumed` | `Entry::RunResumed { base, run_id, attempt }` | Records a crash recovery resume attempt |
| `submission` | `Entry::Submission { base, submission_id, kind, parts, request_id, sender, custom }` | Durable `prompt`, `steer`, `follow_up`, `quiet`, or `mail` input recorded before queueing. `SubmissionKind::Quiet` serializes as `quiet` and never starts a run. `SubmissionKind::Mail` identifies teammate messages; optional `sender` records the roster member name without changing the model-facing mail label. Optional `custom: SubmittedCustom { custom_type, display }` preserves host-message identity and display policy; host `post` stores its text as one `Text` part and bypasses skill expansion. `parts` holds the prepared [prompt parts](prompts-and-context.md#prompt-parts-cratesaxosrcinputrs) as sent (`Saved` instead of `Content`, skill commands unexpanded); model-facing text lives on the consuming `message` entry. Older files wrote `content` (text blocks), loaded through `#[serde(alias = "content")]` as `Text` parts. Built-in commands write no submission |
| `job_start` | `Entry::JobStart { base, session_id, job_id, call_id, command, artifact, started_at, tool, cwd, promotion }` | Written in one batch immediately before the tool result that promotes `bg_N`, or the foreground result retaining helpers (not admitted; reserves the id only). `sessionId` identifies the owning session; forks retain it. `artifact` identifies the output spool. `startedAt` is the spawn time in epoch milliseconds; `tool`, `cwd`, and `promotion` record the tool name, working directory and promotion cause (`async`, `timer`, `steer`, `host`). Older files default `startedAt` to 0 and the optional fields to absent. Never enters model context; ordinary completed foreground commands write no job records |
| `child_start` | `Entry::ChildStart { base, session_id, job_id, call_id, child_session_id, child_path, agent, model, team }` | Creates a child's persistent parent-registry row (`agent_N`). Records parent id, child id/path, optional catalog agent and expanded model. Optional `team: TeamRef` stores the team id and roster member name; absent means a non-team child. Host spawns omit `call_id` and this entry admits the row. Tool spawns record `callId`; their `spawn` result's `admittedJobs` receipt admits the rows. Never enters model context |
| `job_end` | `Entry::JobEnd { base, job_id, text, is_error, partial, run_id, note, exit, usage, value }` | One row message: command result, child-run report or mid-run child note. `jobId` names message 1 as the row alone and later messages as &lt;row&gt;/&lt;n&gt; (n ≥ 2). `partial` and `note` default false and are omitted when false. Optional `runId` identifies a reported child run; notes do not settle it. Optional `exit` records a typed command outcome (camelCase `type` tag). Child-run reports carry optional `usage` (that run's assistant usage) and `value` (an accepted schema-validated result, preserving its JSON type). Commands and notes omit child usage/value. Never enters model context directly; text enters through its delivery message |
| *(unknown)* | `Entry::Unknown(Value)` | Preserved verbatim on load; ignored by projection |

Optional `run_end.usage`, `job_end.usage`, `job_end.value`, `submission.sender`, and `submission.custom` default to absent when reading older files and are omitted when absent when writing; `run_end.queued` defaults to empty and is omitted when empty.

Deferred-tool availability is announced with durable `Entry::CustomMessage` entries of reserved type `tool_catalog` (`display: false`, `details.added` and `details.removed` holding name arrays). Before each provider request, the session folds **all surviving catalog notices in projection order**, applying their additions and removals, and compares that announced set with the current catalog. It appends only the resulting additions or removals. Compaction or navigation can remove some notices; reconciliation then reannounces names absent from the surviving fold, not just from the latest notice. Reopening and navigating also recover native promotions from the projection's system-message tool declarations, restricted to tools still in the live catalog. See [Deferred tools](prompts-and-context.md#deferred-tools).

Mode instructions use durable, non-display `mode_notice` custom messages with `details.mode` naming the effective mode or null on exit. Reconciliation uses the latest notice in projected context, by name only; compaction can remove that notice without removing journal-derived mode state, causing the next request to reannounce the active mode. See [Mode notices and call-time limits](prompts-and-context.md#mode-notices-and-call-time-limits) for exact texts and boundary semantics.

`Entry::usage()` returns the original provider usage of an assistant message, committed compaction or branch summary, or standalone failed-summary usage entry. It returns none for `run_end` and `job_end`: these are rollups, not new spend. Summing this accessor over raw journal entries counts maintenance and failed assistant responses without double-counting run reports or child reports; context edits and projection do not erase historical spend.


## Projection (`crates/axo/src/store/project.rs`)

`project(entries, leaf)` walks the ancestor chain from the current leaf (`None` uses the last entry in the file; an `Entry::Leaf` moves the leaf to its `parent_id`) back to the root:

1. **Latest compaction boundary:** If the root-to-leaf path contains one or more `Entry::Compaction` entries, projection starts from the last compaction's `system_message` snapshot and `compactionSummary` custom message, emits its `preserved_user_ids` in path order, and then replays entries from `first_kept_entry_id` onward.
2. **Branch summaries:** Any `Entry::BranchSummary` on the active segment becomes a `branchSummary` custom message (lowered to a user message).
3. **`ContextEdit` application:** On the active path, the last `Entry::ContextEdit` targeting an entry ID wins. `replacement: None` removes that message from the projection (used to hide transient-error or overflow turns); `Some(ContextReplacement)` replaces its content blocks (used by `/shake` and automatic clearing) and zeroes provider token usage on assistant messages positioned before the last `context_edit` or `compaction` on the path.
4. **Incremental caching (`Projection::apply`):** `Session` maintains the projection incrementally as entries are appended, rebuilding from scratch only when navigating or when an edit/compaction invalidates earlier entries.

Mode and restore metadata are replayed over the entire ancestor chain, before cutting messages at the latest compaction boundary. Compaction therefore does not end a mode or lose its saved selection. A subsequent `ModelChange` or `ThinkingLevelChange` clears the saved restore metadata without clearing the selected mode.

## Root modes

`Session::set_mode(Some(name))` selects a loaded root mode; `Session::set_mode(None)` ends it. An unknown name returns `Error::ModeNotFound`, and a child call returns `Error::InvalidInput` with `Modes belong to root sessions`. Selecting the already-recorded name is a no-op. Selection appends `Entry::ModeChange`, and `Session::mode()` immediately exposes the selected definition, even while its instructions and limits await the next request boundary. Selection alone never starts a run.

The journal stores a mode's name, not a frozen definition. Reopen resolves that name against the current loaded catalog. If it is missing, the session runs without an effective mode and retains the diagnostic `mode "<name>" from the session is unavailable; running without it`; the historical mode entry remains intact. Programmatic mode definitions must be supplied again on reopen. Navigation derives the selection from the target ancestor chain rather than carrying the old branch's mode forward. Forks likewise derive it from their copied path while inheriting the parent's loaded catalog.

`SessionEvent::Mode { mode }` reports selected-name changes, including branch rebasing; `LiveSnapshot::mode` exposes the selected name for attaching hosts. Neither implies that an already-running tool batch has switched policies: effective instructions and limits advance only at the next request boundary. Calls and spawn hooks observe the effective mode, not a selection waiting for that boundary.

### Model restoration

Selecting a mode resolves its optional model selector and clamps thinking to the chosen model's supported level. Model/thinking entries and the mode change are appended together. When a mode changes that selection, its `ModeRestore` records the base provider, model id and thinking level. Switching modes uses the saved base, rather than stacking successive mode overrides; a new mode without a model override returns to that base.

Ending the mode restores the saved selection when its model is still available, otherwise it uses the current selection. Explicit model or thinking changes clear the restore record, so ending the mode does not undo the user's newer choice. As with other model switches, an in-flight request keeps its existing selection. Mode instructions and call-time limits preserve the ordinary system/tool prefix; changing the model itself can affect provider cache reuse.

Mode commands are dispatched through `Session::parse_command` and `Session::run_command`; optional command text is steered only after selection succeeds. See [User commands](prompts-and-context.md#user-commands-cratesaxosrccommandsrs).

### Mode result review

Mode `yield` validates its arguments before execution and preserves the mode on validation failure. For `review: false`, it emits `SessionEvent::ModeResult { call_id, mode, result, awaiting_review: false }` and ends the selected mode, restoring any mode-owned model/thinking selection. For `review: true`, the same event has `awaiting_review: true`, and the call waits for host review with the mode still active. `LiveSnapshot::pending_results` exposes `Vec<PendingResult>` with each pending call's `call_id`, mode name, and schema-validated JSON `result`. These pending registrations are live state, not separate journal entries.

Execution requires its mode definition to be both selected and effective; admission and review registration are serialized with selection changes. Completion clears the selection only if that same mode definition is still selected: a concurrent replacement is left intact and the old yield fails.

- `Session::accept_result(call_id, message)` accepts the result. `Some(message)` overrides `ModeResult::then`; `None` uses that configured continuation. Acceptance returns `Result accepted. Mode "<name>" has ended.` with `\n\n` and the continuation appended when present. With a continuation, the tool does not terminate the run; without one, it sets `terminate: true`. Presence matters: an explicitly empty message still overrides `then` and permits continuation.
- `Session::revise_result(call_id, feedback)` requires non-blank feedback (`feedback must not be blank` otherwise). It keeps the mode active and returns the successful tool text `The result was not accepted. Revise it and call yield again.\n\n<feedback>`, allowing another result attempt.
- `Session::dismiss(call_id)` resolves a pending question or result and cancels the run. The result's dismissal branch reports `The result was dismissed by the user`; cancellation may instead win and report `Operation aborted`. Dismissal does not itself end the mode.
- An actual mode selection change supersedes pending reviews; their tool error is `The mode ended before this result was reviewed.`. Selecting the already-selected mode remains a no-op and does not supersede reviews.
- Cancellation withdraws the pending review and reports `Operation aborted`, leaving the mode selected unless separately changed. A stale yield implementation whose mode is no longer selected or effective reports `yield is unavailable: its mode is no longer active`; the same error prevents completion from clearing a replacement selection.

Settlement or withdrawal emits `SessionEvent::ModeResultResolved { call_id }`, removing the pending item. Accepting or revising an unknown/already-settled call returns `Error::NoPendingResult`. Dismissing an unknown call returns the pending-question error, `Error::NoPendingQuestion`.

Reviewing mode `yield` is `Replay::Safe`: recovery can re-execute an unanswered call and register the review again. Non-review mode `yield` is `Replay::Never`, preventing automatic repetition of an acceptance that may already have changed the mode. Child-output `yield` remains `Replay::Safe`; it has a separate result lifecycle. Accepted result data is exposed in the mode-result event; the durable tool result contains the acceptance/continuation text, not a separate persisted result record.


## Crash Recovery (`crates/axo/src/recovery.rs`)

When `Axo::open_session` opens a session file, `plan_recovery` inspects the journal and projection without filesystem access. `Session` applies the plan and attaches any available command-output artifacts:

- **Unfinished tool calls:** If the last assistant message on the path has tool calls without matching `ToolResult` entries:
  - Tools with `Replay::Never` (`bash`, `edit`, non-review mode `yield`, and `write` to a scheme whose `write_replay` is `Never`) immediately receive a persisted synthetic `ToolResult` with `is_error: true` explaining that the process stopped before completion. `Session` points to any partial command output as `artifact://<n>`, backed by `<session>/artifacts/<n>.<tool>.<escaped-call-id>.log`.
  - Under `RecoveryPolicy::Resume` (default), tools with `Replay::Safe` (`read`, `grep`, `find`, `ask`, `wait`, `spawn`, `enter_mode`, child-output or reviewing mode `yield`, and `write` to a plain path or `local://`) are left unanswered so `Agent::continue_run` re-executes them in the background. A repeated `spawn` call adopts all of its existing children by call id, including every team member.
  - Under `RecoveryPolicy::MarkInterrupted`, `Replay::Safe` calls also receive interrupted results, unconsumed submissions are not requeued, runs whose last response would need response recovery are closed `interrupted` without hiding or retrying, and `Entry::RunEnd { outcome: Interrupted }` is appended immediately.
  - Dispatcher calls are routed to their inner tool name and arguments for replay policy and synthetic interrupted results, preserving the original call id. Partial-output artifact lookup uses that inner name, and an interrupted routed `spawn` admits its already-started children through the synthetic result's receipt, just like a direct `spawn`.
- **Interrupted or failed assistant responses:**
  - If the last assistant response stopped with `StopReason::Length` and had tool calls, every unanswered call receives a truncated-output error result and the run continues.
  - If the last assistant response had a context-overflow signal on a `Stop` reply without tool calls, recovery keeps the reply and closes the run `done` if its maintenance checkpoint already committed (otherwise re-running maintenance). A retryable provider error or overflow with a failed turn hides the failed assistant turn with `Entry::ContextEdit { replacement: None }` and resumes the run.
  - A non-retryable failed or aborted response with unanswered tool calls gets not-executed (or `Operation aborted`) results before the run closes `Failed`/`Aborted`.
- **Unconsumed submissions:** Any `Entry::Submission` saved after the last `RunEnd` (or during an open run), or named in that `RunEnd`'s `queued`, whose `submission_id` has not been consumed by an `Entry::Message` is requeued in order. Other earlier leftovers were dropped with their run. `Steer` and `FollowUp` use their queues; a `Prompt` or `Mail` written after the last `RunEnd` can start the reopened session's run, while held input (named in `queued`) never starts one, matching the live Stop latch. `Quiet` waits for the next boundary or next run without starting one. When recovery itself closes a run (finish, park, or an unresumed terminal response) under `RecoveryPolicy::Resume`, its `RunEnd` holds the run's unconsumed submissions the same way and they are queued without starting a run. Requeued user messages are rendered again from stored `parts`: skill commands expand from the current `SKILL.md`, and saved images are re-read from `local://`. Host submissions carrying `custom` retain their custom type and display flag and bypass skill expansion on recovery too.
- **Restart loop cap (`RESTART_LIMIT = 5`):** If a run accumulates 5 `Entry::RunResumed` markers in a row without an intervening `Entry::Message`, recovery appends `Entry::RunEnd { outcome: Interrupted, reason: "restart_limit" }` and stops resuming it.
- **Interrupted background commands:** Before recovery, every admitted command of this session without a `job_end` receives one (`is_error: true`, `exit: {"type":"interrupted"}`): `Command was interrupted when the session closed; it may have partially run. Output so far: artifact://<n>` (or `… Its output is unavailable.` when the spool is gone). The result becomes pending delivery; see [Background Job Durability](#background-job-durability). Child runs instead recover from their own journals.

## Attaching, Navigating & Forking (`Session`)

- **`session.attach(from_seq)`:** Snapshots `Attach { missed, live, events }` without waiting on a write in flight. Journal publication, live state, and job-registry locks place every event on one side of the snapshot/subscription split. Entries are not missed or repeated; state-valued events such as `Job`, `Context`, and `AutoPaused` may repeat a snapshot value but are never missed. Agent events following a write (such as `MessageEnd` after its `message` entry) may arrive for an entry already in `missed`:
  - `missed`: all `SeqEntry` items with `seq > from_seq` (or all entries when `from_seq` is `None`).
  - `live`: `LiveSnapshot` containing `run_id`, active `maintenance` (`Compact`, `Shake`, `BranchSummary`), and flattened run fields: `running`, partial `streaming` message, `pending_tool_calls`, `queued_steering`, and `queued_follow_up`; plus projected `messages`, `pending_questions`, `pending_results`, `jobs` (`Vec<JobInfo>`), `usage`, live `model`, `thinking`, the selected persona name in `agent`, and selected mode name in `mode`. `context: Option<ContextUsage>` matches `Session::context_usage()` and carries the projected-context estimate plus current model window, trigger, and reserve; `auto_paused: bool` exposes the automatic-continuation latch. Usage sums `Entry::usage()` over all raw journal entries, across branches, including maintenance and failed responses, but excluding run/job rollups and unpersisted streaming tokens; hosts keep it current with `usage += entry.usage()` for each later `Entry` event. It is session-local, not a descendant aggregate, and distinct from current context usage. `Session` owns live run state and event delivery; queue contents come from `Agent::queued()`.
  - `events`: a `tokio::sync::broadcast::Receiver<SessionEvent>`. If a slow receiver lags, it can call `session.attach(Some(last_seen_seq))` to catch up without stalling the agent loop.
- **`session.navigate(target, NavigateOptions { summarize, focus })`:**
  - Appends `Entry::Leaf { base: EntryBase { parent_id: target, .. } }`, records `ModelChange` / `ThinkingLevelChange` / `AgentChange` if the live selection or persona differs from the target branch's, restores the file ledger and nested context tracker to the new projection, and updates the agent's transcript.
  - Running command jobs and children keep running. Their messages are delivered on whichever branch is selected when they finish; delivery names the originating command or child agent.
  - With `summarize: true`, first summarizes the abandoned branch with a separate tool-free request (the `BRANCH_SUMMARY` prompt, plus the [focus](#focus) when given) and appends `Entry::BranchSummary` at `target` in place of the `leaf` entry. If the abandoned branch has no summarizable messages, a plain `leaf` entry is written instead. `focus` without `summarize` returns `Error::InvalidInput`.
- **`session.fork(entry_id)`:** The fork inherits the parent's `EffectiveConfig` and ordered `ToolPolicy` values from `SessionOptions::tool_policies`, and never calls the `ConfigSource`.
  - Copies the root-to-`entry_id` ancestor chain into a new session file whose `Header` records `parent_session` and `forked_from`.
  - Copies the parent's side files into the fork's session directory: `artifacts/` (hard-linked read-only, copy fallback) and `local/` (copied), so `artifact://` and `local://` URLs, including saved prompt content, resolve in the fork. The output spool of a job that is still running (or retaining helpers) is never hard-linked: the fork gets a read-only snapshot copy, so later output appended by the parent's job does not show up in the fork. Copying is best effort; an entry that cannot be carried over is logged and skipped.
  - The fork gets its own empty job registry: no running command handles or child rows carry over, and copied `job_start` / `child_start` records of the parent's session are ignored (their `session_id` differs). Each namespace numbers from one past the highest raw record or receipt naming it.
  - If `entry_id` is a user message, `fork` copies up to that user message's parent and returns `Fork::editable: Option<Vec<PromptPart>>` so a client can prefill its editor, chips included: the parts of the `submission` that produced the message, or, for a message without one (older sessions), one `Text` part joining its text blocks. The returned parts can be resubmitted as-is (`Saved` parts resolve to the copied `local://` files).
  - Any open run on the copied path is closed with `RunEnd { outcome: Interrupted, reason: Some("fork") }` (a run whose last response already settled it is closed with that outcome instead).

## Background Job Durability

A `bash` call promoted to the background (see [Background Jobs](prompts-and-context.md#background-jobs-cratesaxosrcjobsmodrs-cratesaxosrcjobscommandrs) for the model-facing behavior) is tracked by the session's `JobRegistry` and journaled so its result reaches the transcript **exactly once**, across navigation, crashes, and reopen.

- **Admission:** The promoted tool result carries `admittedJobs: ["bg_N"]` and is written in one batch with the job's `job_start`, the start first, so a receipt never names a job whose start is not on disk. A job becomes deliverable only once that batch commits; a `job_start` whose receipt never committed is ignored. A retained `job_start`, written with the foreground result of a command that exits leaving helpers running, has no receipt either: on reopen it is not a job, but its `bg_N` is counted so the id stays reserved. Tools never write journal entries themselves.
- **Result:** When the job's root command ends, its result is stored at once (`proc://` shows it). Its `job_end` is appended as soon as the command has ended and its admitting batch has committed, by whichever happens second; then the result becomes pending. So `job_end` always follows its `job_start` and receipt, and a job whose receipt never committed writes no `job_end`. A job ending while the session shuts down writes no `job_end`; reopen reconciles it as interrupted. A failed `job_end` write is logged, and the result still becomes pending in memory; a persistent journal failure then surfaces through the next receipt-bearing message write.
- **Delivery receipt:** A pending result is reserved for exactly one message: a `wait` tool result, or a `job_result` custom message (`Background job results:` …). That message's entry carries `deliveredJobs: ["bg_N", …]`. Only a committed entry consumes the result: if the write fails, or the reserving message is a synthetic result (aborted or never-executed `wait`), the reservation is released and the result is delivered again later. Delivery is counted at transcript commit, not at provider acceptance: once committed, the result is part of the transcript, and a later failed or retried provider request never resends it as a new message.
- **Raw reconstruction:** On open, the registry is rebuilt from **all raw entries** of the file, not the projected branch, so receipts on abandoned branches still count. For each `job_start` of this session: admitted and delivered → done; admitted and ended but not delivered → pending; admitted and not ended → reconciled as interrupted (see [Crash Recovery](#crash-recovery-cratesaxosrcrecoveryrs)). Command and child ids have separate counters, each one past the highest name in any raw `job_start`, `child_start`, `job_end`, admission receipt, or delivery receipt, so an id the model has seen is never reused. A second open finds the `job_end` and writes nothing.
- **Read-only replay:** `jobs_from_entries(&header, &entries)` uses the same raw-entry reconstruction without reconciliation or writes. An unfinished command remains `Running` as last recorded. Command `promoted_at` and `ended_at` come from `job_start` and `job_end` entry timestamps; `started_at` is the persisted spawn time. Delivery receipts restore message delivery status; live-only child residency/progress are absent.
- **No wake on open:** Opening a session never starts a model run for pending or interrupted results. They reach the model with the next prompt (ahead of the user's message), at the steering point of a run that recovery resumes, or through `wait`.
- **Root result vs. retained helpers:** A command's result is its root shell's: it returns once the root exits plus a fixed 100 ms output drain. Descendants still alive in the command's container stay supervised as `bg_N` with status `helpers running`, keep writing to the same spool, and can be inspected through `proc://` and stopped with `kill`. Their later exit never produces a second result or delivery (see [Background Jobs](prompts-and-context.md#background-jobs-cratesaxosrcjobsmodrs-cratesaxosrcjobscommandrs)).
- **Idle wake:** When a pending result appears while the session is idle (no run, no maintenance), `Session` starts a run whose prompt is the `job_result` message. During a run, results are injected at the next turn boundary, after the current tool batch; they never count as a steer.
- **Stop latch:** `Session::abort` stops only the current turn and its foreground command; background jobs keep running. If a run was active, the Stop latches automatic continuation off. The latch is also set when a run settles with any outcome other than `Done` (error, abort, interruption, persist or journal failure). While latched, finished results and parent-directed notes stay pending instead of waking the session; the next `prompt`, `steer`, `follow_up`, host `post` with `HostDelivery::Steer` or `FollowUp`, or incoming teammate mail clears the latch and carries them. `HostDelivery::Quiet` neither clears the latch nor starts a run. A Stop while idle sets nothing. Hosts observe the latch through `LiveSnapshot::auto_paused` and `SessionEvent::AutoPaused { paused }`.
- **Shutdown:** `Session::shutdown` cancels and waits for the active run, recursively shuts down live children, then stops every open command job and awaits its task. Dropping a `Session` kills its command containers and releases its table-owned child handles; independently held child handles can remain live. Cleanup reaches what the selected container tracks: process-group mode cannot see descendants that called `setsid`, and both modes are best effort if the session process dies without running shutdown.

## Child sessions

`Session::spawn`, `Session::spawn_team` and the model's `spawn` tool create separate durable sessions and start their first prompts asynchronously. A child is not a fork: it starts with its own prompt and transcript, and its header's `SpawnLink` persists the resolved `AgentSpec`, including defaults, output schema, and spawn-hook replacements. Revival uses that spec rather than reloading its catalog definition. `SessionInfo::spawn` exposes the link in session listings; `Session::spawn_link` exposes it on a live child. See [Spawning child sessions](extending.md#spawning-child-sessions) for the host API and [Spawning and returning results](prompts-and-context.md#spawning-and-returning-results) for the model tools.

Children have no root-mode selection or inherited mode instructions. At spawn time, the parent's effective mode limits intersect the resolved child's tool list after all spawn hooks; this list is persisted in `SpawnLink::spec`. Revival reuses those restrictions even if the parent's mode has since changed or ended. Normal child lifecycle-tool rules still apply; see [Mode notices and call-time limits](prompts-and-context.md#mode-notices-and-call-time-limits).

### Rows, run messages, and delivery

- **One row per child:** The parent's `JobRegistry` gives each child one `agent_N` row for its lifetime. Each settled child run and each mid-run note adds a message to that row; later prompts do not allocate a new row. A command has only its single result. Team rows additionally carry `TeamRef { id, member }`; team ids (team_N) are numbered per parent, rebuilt past the highest id in raw child-start records.
- **Admission and replay:** A new child is claimed and its task saved as an unconsumed `submission` in its own file before the parent writes `child_start`, so the task runs before any steer, follow-up or mail and survives a crash. Host spawns are admitted by `child_start`. Tool spawns record `callId` on creation and admit rows only when the `spawn` result commits its `admittedJobs` receipt. A team's child-start entries are appended in one batch; its result admits every member in roster order. Messages completed before admission are held, neither journaled to the parent nor delivered until admission commits. Failed admission aborts the live children. On reopen, unadmitted tool rows remain pending and hidden; rerunning the safe call adopts every matching row and child file, reconciles their journals, and admits them through the rerun's result. If recovery marks that call interrupted instead (`RecoveryPolicy::MarkInterrupted`), the interrupted `spawn` result names the children the call started, carries their `admittedJobs` receipt and admits them; a run parked by the restart cap (`run_end` with `reason: "restart_limit"`) writes no tool results, so that call's tool-spawned children stay pending and dormant.
- **Message references:** Message 1 is named by its row alone; later messages append a slash and a canonical decimal sequence number starting at 2. `job_end` and `deliveredJobs` use these message references, while `admittedJobs` names rows. Delivered text still labels each result with the row, not the sequence number.
- **Run outcome:** Without an output schema, a successful run reports its last non-empty assistant text, joining text blocks with newlines, or “(no text output)”. Failed, aborted, and interrupted runs report their failure/stop reason instead. With an output schema, an accepted `yield` supplies the result (raw text for strings, compact JSON otherwise); an unyielded answer or failed run is an error with the last rejected attempt or last answer, while abort/interruption retains its stop report. The parent receives one `job_end` per child run, deduplicated by `runId`; a task that fails before starting a run reports a startup error without a run id.
  - For a routed child `yield`, reconstruction matches the successful inner-named tool result to the assistant call by id and decodes the dispatcher's inner `args` using the output schema.
- **Exactly-once delivery:** Child messages use the same durable reservation and delivery receipts as command results, through `wait` or a `job_result` message. A committed receipt consumes only that message, not the child row. A failed run-report journal write removes the in-memory message so reopen can derive it again from the child's journal. Notes are instead saved directly in the parent's journal before the sender's tool result; a failed send reports an error, and `send` uses `Replay::Never` so recovery never repeats it. Delivery labels and caps are documented under [Results in context](prompts-and-context.md#results-in-context).
- **Parent reopen:** After registering the parent's registry, open starts a background task that reads each admitted child's journal, one child at a time, and reconciles its completed runs, skipping runs the parent already has a report for; `Axo::open_session` returns without waiting for it, so reconciled results arrive as pending messages shortly after. A child that cannot be read or revived is logged and skipped; it never fails the parent's open. Pending tool-spawned children are reconciled only when their spawning call reruns. It revives children with unfinished runs or unconsumed submissions under `RecoveryPolicy::Resume`; settled children are registered as parked. Messages discovered during reconciliation do **not** wake the parent: they wait for its next prompt, a resumed run's steering point, or `wait`. A revived child that finishes later follows normal live delivery and can wake an idle parent unless the Stop latch is set.
- **Teammate mail:** Mail is a receiver-side `submission` with `kind: "mail"` and optional `sender` roster name, not a parent-registry row message. Its eventual user `message` carries the `submissionId`, so recovery can distinguish consumed from queued mail. Mail is delivered at the next turn boundary or run start; a waiting member returns for mail and reads it after the tool batch. It never sets the steer signal. An idle or user-stopped member starts a run for new mail. See [`send`](prompts-and-context.md#send) for routes and sender labels.

### Budgets and lifecycle

- **Turn budget:** Each new or resumed child run resets its request counter. At `maxTurns`, calls other than `yield` are blocked with “turn budget exhausted” without changing the tool list. If that turn contains tool calls, a `turn_budget` custom message asks for a final answer stating completed work, remaining work, and hand-off needs, or tells an output child to call `yield` with its best final result. Other calls in the following wrap-up request are blocked with `terminate: true`, ending the run; a text-only answer ends normally for a child without an output schema. A run containing the wrap-up notice reports `partial: true`, and delivery adds “(partial: turn budget exhausted)” to its label. An answer that finishes before needing the notice is not marked partial.
- **Concurrent runs:** All descendants of one root and its live forks share `subagents.maxConcurrent` FIFO run slots; a child holds its slot for the whole run, including tool waits. Root runs do not take slots. Teams larger than the limit are rejected. A team's first runs reserve all member slots together, then split one permit per member; subsequent member runs queue individually. With nested spawning enabled, children waiting for descendants can still exhaust all slots; the limit does not release slots during `wait`. Team [mutual-wait detection](prompts-and-context.md#wait) handles members waiting without pending work, not arbitrary nested-spawn slot deadlocks.
- **Host state:** A child waiting for a run slot reports `JobStatus::Queued`, then `Running` once it owns the slot. Child rows expose nesting depth and admission time; residency tracks whether the child session is loaded. `ChildProgress` reports the current or last observed run's request count, budget, wrap-up flag, yield failures, and assistant usage; it is absent until the first assistant message completes and after reopen until new progress arrives. See [job state](extending.md#background-jobs-for-hosts) for the typed fields.
- **Parking and revival:** An idle child with no maintenance, open jobs, pending row messages or mail releases the session table's strong handle. External `Arc<Session>` handles keep it live; otherwise its writer can close. `Axo::session` returns an existing live handle or revives a known parked child from its journal, recorded model/thinking selection, and persisted spec/team link. It does not start a new prompt for a settled child.
- **Follow-ups and steers:** `Session::follow_up` waits until an active run would otherwise finish; `Session::steer` is read after the current tool batch. Both start a run on an idle session, and input arriving after the last drain point starts the next run. That run begins with the next steers per `steeringMode`, else the next follow-ups per `followUpMode` (`Agent::take_next_input`); the rest drain at its own drain points. Parent-side `send` calls to a child use the same APIs after revival; the reply becomes another run message on the existing row.
- **Stop and shutdown:** Stopping the parent does not stop children. `Session::kill_job` on a child row aborts that child's current run, including one still waiting for a run slot: a Stop on a claimed session that has no run yet cancels the run as it starts, which ends it as stopped before any model request. Parent `shutdown` recursively shuts down live children without writing a terminal `run_end` for shutdown-cancelled runs, so reopening the parent resumes them. Dropping a parent releases its owned child handles; a child retained independently by the host can finish while the parent is closed, and its report is reconciled on reopen.

## Manual `/shake` (`Session::shake`)

`session.shake(mode)` shrinks projected context without calling a model. It is also the [built-in command](prompts-and-context.md#user-commands-cratesaxosrccommandsrs) `/shake <mode>` (`elide`, `images`, or `thinking`; `ShakeMode` serializes lowercase). Maintenance emits `SessionEvent::MaintenanceStart` and `SessionEvent::MaintenanceEnd`, and returns `Error::Busy` while a turn or maintenance is running (`Error::MaintenanceAborted` if cancelled):

| `ShakeMode` | Behavior |
| :--- | :--- |
| `ShakeMode::Elide` | Outside the newest `4,000` tokens, replaces tool-result text blocks and fenced/XML blocks in user or assistant text of `>= 400` tokens with `[shaken ~N tokens; full text: artifact://<n>]`, writing the original text to `<session>/artifacts/<n>.shake.txt` first. Skill spans (`<skill …>…</skill>`), `SKILL.md` read results, system messages, compaction summaries, and tool-call arguments are never touched |
| `ShakeMode::Images` | Replaces every `UserBlock::Image` in user, tool-result, and custom messages (except messages containing a skill span) with `[shaken image; full image: artifact://<n>]`, writing the decoded image bytes to `<session>/artifacts/<n>.shake.<ext>` |
| `ShakeMode::Thinking` | Replaces each `AssistantBlock::Thinking` with `[shaken thinking; full thinking: artifact://<n>]`, saving that block's JSON to `<session>/artifacts/<n>.shake.json` (skipped in messages containing a skill span) |

All shake modes leave `mode_notice` and `tool_catalog` custom messages untouched, preserving their instructions and catalog deltas. Automatic recoverable clearing also preserves these notices.

Each modified message receives one `Entry::ContextEdit`. Because edits are append-only, navigating to the entry before the shake restores the unshaken view.

## Manual Compaction & Focus (`Session::compact`)

`session.compact(focus)` (the built-in command `/compact [focus…]`) runs a summary checkpoint right away, without checking the automatic trigger and even with `compaction.enabled: false`. It never takes the clearing shortcut, so it always asks the model for a summary (live or separate per `compaction.summaryRequest`), and commits an `Entry::Compaction` with `reason: manual`.

### Focus

`focus` is the user's plain-text direction for what a summary should prioritize (`/compact keep the auth decisions; drop the exploratory logs`). It goes after the format template in every summary request of that pass (the first or update checkpoint, a split turn's prefix, or a branch summary), outside the `<conversation>` and `<previous-summary>` data tags, because it is an instruction rather than data:

```text
Focus from the user: <focus>
Give it priority, but keep every section of the format.
```

The focus is saved on the committed entry's `focus` field. Automatic and overflow compaction never have one.

## Automatic Compaction (`crates/axo/src/compaction/`)

### Window and trigger math (`Limits::resolve`)

```text
W           = min(model.context_window, compaction.max_context)
reply       = min(model.max_tokens, 32_768)
reserve     = compaction.reserve_tokens.unwrap_or(min(reply + 4_096, W / 4))
trigger     = W - reserve
keep_recent = compaction.keep_recent_tokens.unwrap_or(min(20_000, trigger / 4))
```

`Limits::resolve` fails with `Error::Compaction` when the context window, output limit or cap is 0, when `reserve >= W`, or when `keep_recent >= trigger`.

Context tokens are estimated from the latest non-errored assistant message's provider-reported usage plus local token estimates (`(utf16_units * 2).div_ceil(7)`, with each image counted as 4,800 UTF-16 units, ≈1,372 tokens) for messages after it, falling back to full local estimation when an edit invalidates earlier usage.

Automatic maintenance checks `estimate > trigger` in `prepare_request` (before a prompt and between tool turns) and in `finish_turn` (after a turn settles).

### One action per pass: clearing vs summarization

When `estimate > trigger`, `axo` evaluates two candidates locally:

1. **Recoverable clearing (`elide::prepare`):** Protects the newest `40,000` tokens of tool-result content and elides older eligible tool-result text into `<session>/artifacts/<n>.shake.txt` markers (`[shaken ~N tokens; full text: artifact://<n>]`). Clearing is chosen **only** if the resulting context estimate is at most `trigger - 20,000`, and is skipped when `trigger < 20,000`.
2. **Checkpoint summarization (`Entry::Compaction`):**
   - **Cut point:** Walks backward from the end of the transcript accumulating `keep_recent` tokens and cuts at the first valid boundary (`User`, `Custom`, or `Assistant`, never a `ToolResult`). Message-less records just before the cut (`run_start`, `submission`, `run_end`, settings changes) stay with the kept tail; a cut at a `User` or `Custom` message is always a complete-turn boundary, so only history is summarized. If a single turn exceeds the budget, the turn is split at an `Assistant` boundary and its prefix is summarized with the `COMPACTION_SPLIT_TURN` prompt and merged with the history summary.
   - **Live summary (`SummaryRequest::Live`):** Appends the summary prompt to the live uncleared conversation with `ToolChoice::None` so the request reuses the provider's prompt cache. A live response with a tool call, a non-`Stop` finish, empty text, or text not strictly smaller than the messages it replaces is rejected, and the next attempt uses a separate summary request. A retryable error is first retried in place under `RetrySettings`. Aborts, fatal provider errors, and an overflowing separate request end the pass.
   - **Separate summary (`SummaryRequest::Separate`):** Serializes the messages to summarize into `<conversation>` text and sends a tool-free request under the `SUMMARY` prompt.
   - **Carryover:** The committed `Entry::Compaction` stores the current `SystemMessage` snapshot, `preserved_user_ids` (recent whole user messages from the summarized region that fit within `keep_recent`), `details: {"readFiles": […], "modifiedFiles": […]}`, and the summary text. `summary` stores the model text followed by `Session history: <path>` and `<read-files>`/`<modified-files>` lists. Lists accumulate across checkpoints, and modified paths are removed from the read list. File lists come from successful `read`, `write`, and `edit` results and use absolute paths.
   - **Escalation bound:** Automatic maintenance attempts one clearing attempt, then at most 3 summary attempts (falling back to a separate request after a failure) before failing with `Error::Compaction`.

## Transient Retry & Overflow Recovery

- **Transient retry:** `axo_ai::is_retryable_error` and `axo_ai::is_fatal_error` classify provider errors; `axo::RetrySettings` owns turn and summary retry policy. When a turn ends with a retryable provider error (`HTTP 429`, `500`, `502`, `503`, `504`, `520`, `524`, stream transport errors, or `overloaded`/`rate_limit`/`too many requests`/`service_unavailable`/`server_error` without quota exhaustion), `Session` hides the failed assistant message with `Entry::ContextEdit { replacement: None }`, emits `SessionEvent::Retry { attempt, delay_ms }`, sleeps, and retries within `retry.maxRetries`. Defaults are 3 retries with 2/4/8-second exponential delays; a server delay hint replaces the backoff, but a hint above `retry.maxDelayMs` (default 60,000 ms) stops retries. `retry.baseDelayMs` sets the backoff base, `retry.maxRetries: 0` disables retries, and an unrepresentable backoff stops retries.
- **Fixed transport retries:** before a response body is consumed, `axo_ai` separately allows 2 request-level retries. This transport detail is not controlled by `RetrySettings`; it honors server delays up to 60 seconds. A longer hint returns the failed response without sleeping so the adapter preserves the hint for the configurable turn-level policy.
- **One-shot overflow recovery (`axo_ai::is_context_overflow`, `axo_ai::is_recoverable_length`):** When a turn fails with context overflow (or stops with `StopReason::Length` when output is 0 and input + cache_read >= 99% of context window, or output is below requested max_tokens) and `compaction.enabled` is `true`, `Session` hides the failed turn and any tool results it produced, runs recoverable clearing followed by a separate-request compaction pass if needed, and retries once within the same run. A context-pressure signal on a successful reply without tool calls keeps the reply and runs one overflow compaction pass (always a separate summary request) without retrying.
